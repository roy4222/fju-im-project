# 模組實作設計 01｜帳號與權限（v2.4）

## 1. 使用者要完成的工作與案例
- 產品原文：[01 帳號與權限](<../../product/🧩 功能模組/01 帳號與權限.md>) §2.3–2.6、2026-09-12 定案；母 spec 故事 US-03、04、05、19、28、29、30。案例：ACC-01–11、13–18（ACC-12 空號）。
- 工作：系辦匯入名單並核實核准每一位註冊者；學生註冊後看得到狀態並能修正；老師由系辦建立或預授權後補資料；系辦停用、還原、發臨時密碼、撤 session；本人連結另一種登入方式；每個人只做自己角色的事。
- 校方待辦：ACC-03a／b／c（CSV 樣本、Google 帳號種類、核實 SOP）；不阻塞實作，阻塞真實名單匯入與真實核准。

## 2. 名詞與不變量（本模組擁有）
- 登入身分（`users.email`／Google account）本人不可改；聯絡 Email 在 `user_profiles.contact_email`。
- 首次註冊不論路徑 `users.status='pending'`；只有 `ApproveRegistration` 把它變 active，且必記核實方式；核准同時寫 `student_identities` 占用有效學號。
- 同屆同學號只能有一個 active 學生（占用表唯一）。
- 同一 Google 身分只綁一個帳號；連結只由本人 fresh session 發起。
- 停用立即撤 session；must-change 期間只允許改密與登出；pending 與 must-change 可以重新登入取得受限 session。
- 名單比對只產生 `roster_match`，不改狀態。
- 「這次登入方式」來自目前 session 列 `sessions.login_method`（契約 01 §4.1）；`user_profiles.login_method_last` 只是帳號最近一次登入方式的顯示欄，不作任何判定。
- v2.1（Codex RR02）：`role_assignments` 的結束欄統一為 `revoked_real_at`；撤 session 的重試狀態移到可變工作表 `session_revocations`，`user_status_events` 維持不可變。
- v2.4（Codex 第五輪 D1）：`session_revocations` 改為「一個狀態事件一筆主工作＋多筆收斂工作」——新增 `trigger`／`reconcile_reason`／`reconcile_of_id`／`reconcile_round`，`status_event_id` 的唯一鍵改為部分唯一，`attempts` 移除，收斂插入以「每人同時最多一筆未結收斂工作」為冪等鍵；收斂核對改讀 Better Auth admin plugin 自己寫在 `users.banned` 的套件欄（`fju_app` 唯讀查詢，不呼叫 `auth.api.listUsers`，`/admin/*` 維持封鎖）；正常完成的順序保證與逾時後的最終收斂保證分開寫，並附逐列序列（附錄 A）。

## 3. 狀態表
| 狀態 | 觸發者 | 前置 | 轉移與寫入 | 拒絕 | 回執 |
|---|---|---|---|---|---|
| （無）→ pending | 註冊者 | Email 未用；Google 身分未綁他人 | 建 user＋profile＋application(pending, revision 1)＋roster_match | `USER_EXISTS`（統一訊息）、`ACCOUNT_LINK_CONFLICT` | 申請 ID、比對摘要 |
| pending（修改） | 本人（受限 session） | application pending | revision+1、`application_revisions`、重新比對 | — | 新 revision |
| pending → active | 管理員 | application revision 相符；核實方式必選；屆別存在 | `users.status=active`、profile 屆別、`role_assignments(student)`、`student_identities` 插入、`user_status_events`、audit、事件 `account.approved`（不進通知匣） | `CONFLICT`、`VALIDATION_FAILED`、`STUDENT_NO_TAKEN` | 核准紀錄 |
| pending → rejected | 管理員 | 理由必填 | application rejected；user 保留可再申請 | — | 退回紀錄 |
| active → disabled | 管理員 | 理由 | status event、`student_identities` 刪除、commit 後 `banUser`（撤 session；結果經 `session_revocations` 每人序列化執行器（queued→executing→done；失敗不重用同一列，由收斂工作接手，附錄 A 規則 5）） | 不可停用自己 | — |
| disabled → active | 管理員 | 理由 | `student_identities` 重插（唯一違反→`STUDENT_NO_TAKEN`）、`unbanUser` | — | — |
| active → deidentified | 管理員 | 影響預覽二次確認 | profile 清空、email 置換、`deidentified_at`、保留業務關聯與 audit | 有未完成簽核參與→先成員異動 | 影響清單 |
| 臨時密碼 | 管理員 | 核實方式 | `setUserPassword`＋`must_change_password=true`＋`revokeUserSessions`；audit 不含秘密 | — | `SecretOnce`（一次顯示） |
| must-change → normal | 本人 | 改密成功 | 旗標清除、其他 session 撤 | — | — |
| 連結 Google／設密碼 | 本人 | active、fresh session | `linkSocial`／`setPassword` | `ACCOUNT_LINK_CONFLICT`、`FRESH_SESSION_REQUIRED` | 帳號 ID 不變 |
| 老師建立／預授權 | 管理員 | Email 唯一 | `createUser`（伺服器端）＋`role_assignments(teacher)`；預授權以 `users.status='active'` 但 profile 待補 | — | — |

## 6. 交易、並行、時間
- 核准：`registration_applications` `FOR UPDATE`＋revision；`student_identities` INSERT（唯一違反→`STUDENT_NO_TAKEN`，整體回滾）；同交易呼叫 05 `syncRoster`；`banUser`／`unbanUser` 在 commit 後；經 `SessionRevocationExecutor` 排隊執行並寫 `session_revocations`，不回頭改 `user_status_events`。
- 名單匯入整批一交易；`(roster_version_id, student_no)` 唯一違反已在預覽列重複，匯入跳過並記錄。
- 時間：核准、停用用 RealClock；audit 雙時間。

## 10. 自動測試
單元：正規化、CSV 去重與衝突、roster_match。用例：apply→pending；approve 缺核實方式；revision 過期；占用表衝突；reject 保留 user；deidentify 不斷關聯。整合：路由矩陣（pending 受限 session、must-change、disabled、封鎖端點）、內部呼叫辨識正反向、banUser 後舊 session 為 null、`SecretOnce` 不入 DB／log／trace 掃描、linkSocial 衝突、Turnstile 伺服器驗證六條路徑。對應 ACC-01–11、14、15、17、18（ACC-13、16、18 真 Google 由 Roy）；`session_revocations` 全程（核准→停用→撤 session 失敗→重試成功）；以 `fju_app` 跑核准、改密、修改個資、連結的正向流程（契約 01 §5）；停用（ban 失敗）→恢復成功→舊 ban 重試被取消、帳號仍可登入（A3）；C1 三個序列（核對後、外部完成前插入恢復；租約過期後收斂；連續三事件）以同步屏障測試，最終 Better Auth 狀態與 `users.status` 一致且帳號可登入。D1 釘版測試（v2.4；S01 負責執行器與讀取，S02 負責 worker 週期核對）：（1）`readBanned` 唯讀查詢——內部包裝呼叫 `banUser` 回傳後立即為 true、`unbanUser` 後為 false、在沒有 request context 與 session 的環境可呼叫；（2）反向——外部 HTTP `POST /api/auth/admin/list-users` 與 `/admin/ban-user` 帶管理員 session 仍被擋，缺 marker 的伺服器呼叫也被擋；（3）安裝後 gate——admin plugin 在 `users` 產生的 `banned`／`ban_reason`／`ban_expires` 欄名與實際 drizzle schema 一致；（4）附錄 A 逐列序列（b）的列級斷言：R1 failed／`lease_expired`／`outcome_unknown`、R2 done、R3 `trigger='reconcile'`／`reconcile_round=1`／指向 E2，最終 `readBanned=false` 且可登入；（5）兩個核對者同時插入只留一筆（第三條部分唯一，`ON CONFLICT DO NOTHING`）；（6）同一狀態事件自動收斂到 round 10 的列直接 failed `RECONCILE_LIMIT`、寫 audit 與告警，之後 worker 不再自動插入，新狀態事件 round 歸零、`manual_retry` 仍可排入；（7）owner fencing——租約被接手後原執行者的完成結果被丟棄；（8）順序保證——前一筆外部呼叫有回傳時，後到事件的呼叫必在其後開始（屏障量測）。

**規則（v2.4，Codex C1＋D1：涵蓋已開始的外部呼叫，且收斂工作寫得進去）**——所有對 Better Auth 的 `banUser`／`unbanUser`／`revokeUserSessions` 只經同一個 `SessionRevocationExecutor.runForUser(userId)`，用例 commit 後的立即呼叫、worker tick、管理端「重試」都是呼叫它，沒有第二條路：
1. **排隊**：停用、恢復、去識別化用例在業務交易內插入一筆主工作 `queued(trigger='status_event')`（記 `status_event_id` 與 `expected_user_status`、推得 `kind`），並把該使用者其他 `queued`（含收斂工作）標 cancelled（`superseded_by_event`）；**不動 `executing`**（已開始的外部呼叫不能取消，只能等它結束再覆蓋）。
2. **認領（短交易）**：對該使用者的工作列 `FOR UPDATE`；若有 `executing` 且租約未過期→不做事（由該執行者結束後接續，或 worker 下一輪）；若 `executing` 租約已過期→標 failed（`lease_expired`、`outcome_unknown=true`）；取最新的 `queued`（其餘 queued→cancelled `superseded_by_event`）；若它的 `status_event_id` 已不是該使用者最新的狀態事件→cancelled（`status_mismatch`）並結束本次認領（新事件的主工作會自己排入）；否則標 executing、寫 `lease_owner`、`lease_expires_at=now+30s`，並在同交易重讀 `users.status` 覆寫 `expected_user_status` 與 `kind`（以認領當下的最新狀態為準）。
3. **執行（交易外）**：依 `expected_user_status` 呼叫 Better Auth（disabled→`banUser`；active→`unbanUser`；deidentified→`revokeUserSessions`＋`banUser`），逾時 10 秒；這些呼叫是冪等的。
4. **完成（短交易）**：`FOR UPDATE` 工作列；只有仍是 executing 且 `lease_owner` 是自己才寫 done／failed（否則視為已被接手，本次結果丟棄）；逾時或例外→failed 並 `outcome_unknown=true`；接著若該使用者又有新的 `queued`→回到步驟 2 在同一次呼叫內繼續，保證後到的事件一定在先前的外部呼叫**回傳之後**才執行；沒有 queued 時做規則 5 的完成後核對。
5. **收斂核對（v2.4）**：
   - **讀法**：Better Auth admin plugin 把 `banned`／`ban_reason`／`ban_expires` 寫在 Better Auth 自己的 `users` 表（套件欄，契約 01 §4.1）。核對只用 `BetterAuthUserStateReader.readBanned(userId)`＝`fju_app` 對 `users` 的唯讀 SELECT（Drizzle）；沒有 session、沒有 request、不經 `auth.api.*`。`auth.api.listUsers` 不使用，也不加進契約 03 §2 的內部能力清單；外部 `/admin/*`（含 `list-users`）對任何 session 維持封鎖。安裝後 gate：以實際版本核對產生的 drizzle schema 欄名，並釘一支測試證明內部包裝呼叫 `banUser` 回傳後 `readBanned` 立即為 true、`unbanUser` 後為 false（§10）。
   - **時機與觀察集合**：每次完成後（`after_completion`，只對該使用者）；worker 每 5 分鐘（`periodic`）對「24 小時內有任何工作列的使用者」∪「7 天內有 `outcome_unknown=true` 列的使用者」；管理端「重試」（`manual_retry`，指定使用者）。
   - **步驟（短交易）**：`FOR UPDATE` 該使用者全部工作列；若有 `queued` 或 `executing`→不插入（等它完成後的核對）；否則以 `users.status` 推應有值（disabled／deidentified→應 `banned=true`；active→應 `banned=false`；pending 不核對），呼叫 `readBanned`；一致→不插入，結束；不一致→插入一筆 `queued(trigger='reconcile')`：`status_event_id`＝該使用者最新狀態事件、`reconcile_of_id`＝最新終態列、`reconcile_reason`＝觸發原因、`expected_user_status`／`kind` 依應有值、`reconcile_round`＝同 `status_event_id` 下前一筆自動收斂的 round＋1（沒有則 1；`manual_retry` 沿用前一筆的 round，沒有則 1），插入用 `ON CONFLICT DO NOTHING`（命中唯一鍵③＝已有人排入）；插入成功後在同一次呼叫回到規則 2。
   - **上限**：自動原因（`after_completion`／`periodic`）算出的 `reconcile_round` 到 10 時，仍插入該列但直接 `failed`、`last_error='RECONCILE_LIMIT'`、`completed_real_at=now`，寫 audit（契約 01 §4.3）並發告警（SOP 05）；之後 worker 對該（使用者、`status_event_id`）不再自動插入，只有新的狀態事件（新 `status_event_id`，round 從 1 重算）或 `manual_retry` 才會再排。
6. **入口層不等收斂**：`hooks.before` 與 ActorResolver 一律以 `users.status` 拒絕；Better Auth 的 banned 只是第二層，收斂前的落差不會放行任何業務操作。

**兩種保證分開（v2.4，D1）**：
- **正常完成的順序保證**：只要前一筆工作的外部呼叫**有回傳**（done，或 failed 且 `outcome_unknown=false`），後到事件的呼叫必在該回傳之後才開始（規則 2、4）；因此「停用→恢復」在正常情況下 Better Auth 最終狀態＝最後一個狀態事件。規則 4「回傳之後」限定的就是這種情況。
- **逾時／租約過期後的最終收斂保證**：`outcome_unknown=true` 時不保證順序，舊呼叫可能晚到；只保證在觀察期內（7 天、每 5 分鐘）由收斂工作把 Better Auth 拉回 `users.status`，或在自動 round 10 告警並留下 failed 列由人處理。入口層自始以 `users.status` 拒絕（規則 6），所以落差期間不會有業務操作被放行；只可能出現「業務上應可登入卻被 Better Auth 暫時擋下」，收斂後恢復。
