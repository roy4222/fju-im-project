# SOP 05｜監測與告警

> 2026-10-21 重寫（⑤-08）。舊版的 Gatus、自製「開發者後台」（fju-status）、`ALERT_WEBHOOK_URL`、站內通知都已拆掉，不再適用。現在的做法一句話：**GitHub 每 10 分鐘巡檢兩站，Healthchecks.io 盯排程工作有沒有準時回報，壞消息一律送到 Discord 的監測頻道。** Roy 只需要看 Discord；頻道安靜＝一切正常。
>
> 以程式為準：[`.github/workflows/health-cron.yml`](../../../.github/workflows/health-cron.yml)、[`ops/lib/healthchecks.sh`](../../../ops/lib/healthchecks.sh)、[`ops/backup-daily.sh`](../../../ops/backup-daily.sh)；設定與操作步驟的細節在 [`ops/README.md`](../../../ops/README.md)「Healthchecks.io」「磁碟用量」兩節。本頁與它們不一致時，以程式為準並回頭修本頁。

## 白話版

- **誰在看站活著沒**：GitHub Actions 的 `health-cron`，每 10 分鐘打一次測試站與正式站的 `/api/health`。打不通、回應不對，或背景 worker 超過 5 分鐘沒心跳，就算失敗，Discord 會收到「🔴 健康檢查失敗」。排程的某一輪失敗後，下一次排程成功時，會收到一則「🟢 健康檢查已恢復」。
- **誰在看排程工作有沒有跑**：Healthchecks.io。備份、自動部署、worker 各自跑完會「打卡」；超過時間沒打卡，或打的是失敗，Healthchecks.io 直接送 Discord。
- **磁碟快滿了怎麼知道**：每天備份時順便量，`/srv` 用到 80% 以上就把「每日備份」打成失敗，Discord 訊息會寫「磁碟 NN%」。
- **沒有後台、沒有儀表板**：Roy 只看 Cloudflare、GA4、Discord。

## 監測項目一覽

| 監測什麼 | 誰負責 | 多久一次 | 壞了誰通知 |
|---|---|---|---|
| 測試站 `https://test.fju.roy422.dev/api/health` | GitHub `health-cron` | 每 10 分鐘 | Discord（workflow 的 notify job） |
| 正式站 `https://fju.roy422.dev/api/health` | GitHub `health-cron`（repository variable `HEALTH_PROD_ENABLED` 設 `true` 才跑，開站當天設） | 每 10 分鐘 | 同上 |
| Healthchecks.io「每日備份」 | `ops/backup-daily.sh`（systemd timer，台灣 03:30） | 每天；寬限 2 小時 | Healthchecks.io → Discord |
| Healthchecks.io「自動部署」 | `ops/auto-deploy.sh`（每一輪結束，成功或失敗） | 每 2 分鐘；週期 10 分鐘、寬限 10 分鐘 | Healthchecks.io → Discord |
| Healthchecks.io「worker 測試站」 | 測試站 worker | 每 5 分鐘；週期 10 分鐘、寬限 10 分鐘 | Healthchecks.io → Discord |
| Healthchecks.io「worker 正式站」 | 正式站 worker | 同上 | Healthchecks.io → Discord |
| 磁碟 ≥ 80% | `ops/backup-daily.sh` 量 `/srv` | 每天一次，隨備份 | 「每日備份」check 變失敗 → Discord，內容「磁碟 NN%」 |

Healthchecks.io 共 **四個 check**（三種排程工作，其中 worker 測試站、正式站各一個），免費方案 20 個夠用。

`health-cron` 判定失敗的條件（全部要過才算健康）：HTTP 200 且內容完整、回應的 `ok` 為 `true`、`commit` 是非空字串、`worker.lastTickAt` 在 5 分鐘內。連線問題會先重試 3 次（間隔 30 秒）才算失敗。

## Roy 要做的設定（一次，約 20 分鐘）

1. **Discord**：在「寶寶聚會」伺服器建一個監測頻道，建立 webhook。**webhook 網址等同密碼**，不貼進 repo、issue、PR 或聊天。
2. **GitHub**：repo → Settings → Secrets and variables → Actions，新增 secret `DISCORD_WEBHOOK_URL`（沒設只是略過通知，巡檢本身照跑）。開站當天再新增 repository variable `HEALTH_PROD_ENABLED` = `true`。
3. **Healthchecks.io 與 VM**：建四個 check、接 Discord integration、把 ping 網址放進 VM 的 secrets 檔與 Doppler。完整步驟與指令照 [`ops/README.md`](../../../ops/README.md)「Healthchecks.io（⑤-06）」那一節做，這裡不重複（打卡網址同樣等同密碼）。
4. **驗收**：四個 check 都變綠；到 Actions 手動跑一次 `health-cron`，`test_url` 填一個連不上的網址，頻道應收到下面的「🔴」訊息；收到「🔴」就算通過。「🟢」只在排程那一輪失敗、下一次排程成功時才會送，手動跑不會觸發，所以不用再手動跑一次等它。

## 壞消息長什麼樣

health-cron 失敗（2026-10-21 實測：手動跑 `health-cron`，`test_url` 指向連不上的網址，notify job 顯示「已送出 Discord 通知」）：

```
🔴 健康檢查失敗
- 測試站：連不上（job 結論：failure）
時間：2026-10-21 00:47 UTC／2026-10-21 08:47 台灣時間
run：https://github.com/roy4222/fju-im-project/actions/runs/<run 編號>
```

細節欄可能是「逾時」「連不上」「HTTP 502」「HTTP 200 但內容不對（ok／commit 不對，或 worker 超過 5 分鐘沒心跳）」。恢復時：

```
🟢 健康檢查已恢復
時間：…／…
run：…
```

Healthchecks.io 的壞消息（Discord 訊息的格式由 Healthchecks.io 決定，大意是「某某 check 已 down」或「收到失敗回報」，並帶上我們送的內容）：

- 備份失敗：內容像「正式站備份失敗（exit 1）」。
- 磁碟快滿：內容「磁碟 85%」。
- 某個 check 超過寬限沒打卡：代表那個排程工作沒跑，或整台主機有問題。

## 收到壞消息怎麼辦

| 看到什麼 | 先做什麼 |
|---|---|
| 🔴 測試站／正式站「連不上」「逾時」 | 先看 Cloudflare 與 VM 是否在線；VM 上看 `docker ps`、`docker logs`，依 SOP 03 重啟或回滾 |
| 🔴「HTTP 200 但內容不對」，含 worker 沒心跳 | 多半是背景 worker 掛了：重啟該站的 worker 容器，仍不行依 SOP 03 回滾 |
| 「worker 測試站／正式站」check 沒打卡 | 同上（worker 沒在跑） |
| 「自動部署」check 失敗或沒打卡 | 看 VM：`journalctl -u fju-auto-deploy.service -n 50` |
| 「每日備份」失敗 | 依 SOP 04；磁碟 NN% 則清舊的 `backups/` 與 `offsite/prod/` dump、舊映像，仍不夠就評估加大磁碟（見 `ops/README.md`「磁碟用量」） |

## 怎麼靜音

- **整個頻道暫停**：在 Discord 對監測頻道選「靜音頻道」。health-cron 連續失敗時每 10 分鐘會各送一則，這是刻意設計（不做抑制），煩的話靜音頻道即可。
- **暫時不想收某個 Healthchecks.io 通知**（例如整夜驗收前先關了 timer）：在 Healthchecks.io 該 check 按 **Pause**，恢復時它會自己變回綠。
- **暫停 health-cron**：GitHub → Actions → health-cron → 右上角「…」→ Disable workflow；做完記得 Enable。另外，repo 連續 60 天沒有 commit，GitHub 會自動停用排程 workflow，頻道長期沒消息時順便看一眼它還開著。
