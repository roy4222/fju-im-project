## 步驟與預期（v3 兩站版）

**`ops/deploy.sh --site <站> <SHA> --execute` 的七步**（契約 05 §3 不變，多了站台與取值）：

0. 以該站的 Doppler token `doppler run --no-fallback` 重新執行自己（SOP 02 §1），核對 config 與必要鍵；Compose 以 `COMPOSE_FILE=docker-compose.yml:docker-compose.vm.yml`、`COMPOSE_PROJECT_NAME=fju-<站>` 執行，不需任何 `-f`／`-p`。
1. 取該站的部署鎖（`flock --nonblock`）；拿不到就以 **75** 結束，不排隊。
2. 記錄目前 app 映像與 digest 到 `previous_tag`（第一次部署為空）。
3. `docker compose pull app worker migrate`（`APP_IMAGE=ghcr.io/roy4222/fju-web:<SHA>`）。
4. `docker compose run --rm migrate`（新映像、owner 連線）；取輸出的 `SCHEMA_VERSION`；接著把 `fju_app` 的密碼設成 Doppler 的 `APP_DB_PASSWORD`（SQL 走 stdin，密碼不進指令列與 log；冪等）。失敗即中止，舊 app 繼續跑。
5. `docker compose up -d postgres`、`docker compose up -d --no-deps app worker`。
6. 健康判定：`curl --resolve <站 host>:443:127.0.0.1 https://<站 host>/api/health`（經共用 Caddy 與 TLS，但不繞 DNS），60 秒內比對上列各項；啟動失敗或健康失敗走同一條補償流程（回滾＋重跑健康判定＋寫 `deploy_log`）。
7. 寫 `deploy_log`：`<時間> deployed <SHA> <健康條件> <digest> <schema>`。

**首次部署（每站各一次，手動）**：共用 Caddy 取得憑證後才做（健康判定走 Caddy，沒憑證會失敗且無前一版可退）。`sudo -u deploy /srv/fju/app/ops/deploy.sh --site test <SHA> --execute`；成功後 `curl https://test.fju.roy422.dev/api/health` 的 `commit`＝該 SHA。接著建第一位管理員：`sudo -u deploy /srv/fju/app/ops/seed-admin.sh test`——用同一把 Doppler token 取 `A1_EMAIL`、`A1_INITIAL_PASSWORD`（可選 `A1_NAME`）與 owner 連線，以該站**正在跑的映像**在 migrate 容器裡執行 `seed-a1.mjs`（映像已帶這支腳本與依賴；VM 不裝 node 套件、不裝 pnpm）；A1 值以 `-e 名稱` 轉交、不進指令列、不印；拿該站部署鎖。預期 `A1 已建立：status=active、must_change_password=true、角色 admin`，首次登入強制改密。重跑安全：同一 email 已存在就 rollback 並只印「A1 已存在」。前置：Roy 在 Doppler `stg`／`prd` 確認 `A1_EMAIL`、`A1_INITIAL_PASSWORD` 兩個鍵存在（只核對鍵名；一次性密碼 ≥ 12 字元）。正式站首次部署後同樣跑 `seed-admin.sh prod`。

**自動部署（只有測試站）**：`fju-auto-deploy.timer`（`vm-setup.sh` 安裝；開機後 1 分鐘起、每次結束後 2 分鐘再跑）→ `ops/auto-deploy.sh`：
- 不動作（exit 0）：暫停檔 `/srv/fju/test/deploy/auto-deploy.paused` 存在；測試站 token 未貼；`deploy_log` 沒有任何 `deployed`／`rolled-back`（第一次必須手動）；上一輪還在跑。
- `docker pull ghcr.io/roy4222/fju-web:main`，從 label `org.opencontainers.image.revision`（退而求其次：映像的 `GIT_COMMIT`）取完整 SHA；與 `auto-deploy.last` 相同或測試站已在跑它 → 不動作。
- 有新 SHA → 呼叫 `ops/deploy.sh --site test <SHA> --execute`（失敗照上面自動回滾）。成功或失敗都記下這個 SHA，**失敗的 SHA 不自動重試**（避免每 2 分鐘重啟測試站），等下一次 main 有新映像；exit 75（鎖被人工部署佔住）則下一輪再試。紀錄寫 `auto-deploy.log` 與 journald，不含秘密。
- 腳本固定 `site_setup test`，沒有任何參數能改站台；正式站不會被自動更新。
- 暫停：`sudo -u deploy touch /srv/fju/test/deploy/auto-deploy.paused`；恢復：`rm` 該檔；整個關掉：`sudo systemctl disable --now fju-auto-deploy.timer`。
- 注意：自動部署只換**映像**；`ops/`、compose 檔、`Caddyfile.vm` 有改時要依 `ops/README.md`「repo 的 ops／compose 檔改了之後」手動同步到 VM。

**推正式站（手動，Gate：Roy 接受測試站）**：`sudo -u deploy docker inspect --format '{{.Config.Image}}' fju-test-app` 取測試站正在跑的 SHA → `sudo -u deploy /srv/fju/app/ops/deploy.sh --site prod <同一 SHA> --execute`。同一個映像（同 tag、同 digest）先上測試站、再上正式站。正式站首次部署跑自己的 migrate（空庫），資料不從測試站搬（SOP 06 v3）。

**回滾（指定舊 tag）**：從 `deploy_log` 找之前 `deployed` 的 SHA → `ops/deploy.sh --site <站> <舊 SHA> --rollback --execute`：只 pull app／worker、**不跑 migrate**（舊映像的 migrator 會把 `schema_meta` 寫回舊版本）、不同步密碼、健康判定不比 `schemaVersion`（DB 維持新 schema）；成功記 `rolled-back`，失敗照補償流程退回回滾前那一版。回滾測試站前先暫停自動部署。
