### S05-04 儲存草稿
- **目標**：S01 在 `/items/[id]` 填寫後按儲存→`SubmissionCommand.saveDraft(itemId, receiver, revision, answers, fileIds, requestId)` 在 `drafts` `FOR UPDATE`＋revision 下寫入（第一次儲存建立列，`schema_version_id`＝項目目前 schema 版本，`migration_state='none'`），回執含 revision 與伺服器時間，右下狀態「已儲存 hh:mm:ss（伺服器時間）」；答案以目前 schema 做型別與選項驗證（必填不擋）；舊 revision 儲存回 `CONFLICT` 並保留本機輸入；登出再登入、重載後草稿仍在；他人不能改、直接請求被拒；儲存失敗顯示錯誤，不顯示成功。
- **spec**：模組 05 §3「草稿｜儲存：有效收件者；revision；項目開放；屆別 active」（拒絕 `CONFLICT`、`ITEM_NOT_OPEN`、`COHORT_ARCHIVED`）、§5 `saveDraft`（收件者；requestId）、§6「儲存草稿：`drafts` `FOR UPDATE`＋revision；答案以目前 schema 驗證（必填只在送出擋）」、§7（儲存狀態帶伺服器時間；`CONFLICT` 顯示差異保留輸入）、附錄 A `drafts`；契約 01 §6（鎖序 cohorts→…→頭列 `drafts`）、§8（帳本）；契約 02 §1（DTO 含 requestId 與 revision）、§4（`CONFLICT`：「別人已更新，你的輸入保留在本機」；`UNAUTHENTICATED` 本機輸入放 sessionStorage）、§5（needs_review 草稿的 state 檢查在送出）；契約 03 §1（個人回答寫：本人）；產品模組 05 §7「已儲存須跨重登入保留；儲存失敗須提示」；劇本 P03 步驟 6（儲存草稿）、§6 持久化；案例 SUB-01、SUB-14（追溯）。

## 讀 spec 時發現的問題（不改 spec，只列）
- **`snapshot_reconcile` 的排程與 handler 分屬兩切片**：母 spec §4.10、§4.17 與模組 05 §6 要求正式送出交易內寫 `due_work(snapshot_reconcile)`；handler 本體在 S08 卡；S02 票草稿 S02-07 對「未註冊 kind 標 failed＋告警」。S05 出場時 worker 會把每筆送出的到期工作標 failed 並發管理員告警。同一問題也存在於 E04 已排程的 `deadline_snapshot`（S04-05 排程、S08 才有 handler）。需 Roy 定：S05（與 S04）註冊「保持 pending」的過渡 handler，或 S08 前不排程，或 S02-07 對未註冊 kind 改為保持 pending。
- **完成率公式的分子範圍**：模組 05 §4 寫 `count(distinct receiver having version)/count(eligible & not exempt)`，分子沒有限制在「目前有效且非免填」的收件者；產品模組 05 §4（Q-SUB03）「移出一位已交者變 7／9」與模組 05 §8「移出已交者→7／9」要求分子也只算目前有效且非免填者。本稿依產品定案實作，建議 §4 公式補「分子限目前有效且非免填」。
- **個人送出是否產生事件**：產品模組 08 §4 矩陣「正式送出版本→其他有效組員；老師不收」，個人收件沒有其他組員；同節又寫「每次真正成功的業務變更產生固定事件 ID」。個人送出要不要寫一筆無收件人的 `domain_events`（供追溯）未定義；本稿預設不發。
- **`SCHEMA_INVALID` 與 `VALIDATION_FAILED` 的分界**：模組 05 §2 守門順序只有「schema（`DRAFT_NEEDS_REVIEW`）→欄位驗證（`VALIDATION_FAILED`）」，但 S05 卡「拒絕」與母 spec §4.17 錯誤碼列 `SCHEMA_INVALID`，契約 02 §1 兩碼都在「輸入」類。本稿暫定：答案結構不符 schema（未知 key、型別不符、選項外）→`SCHEMA_INVALID`；欄位規則（必填）→`VALIDATION_FAILED`；需 Roy 或 Codex 確認並補進模組 05 §2 的順序。
- **截止後儲存草稿**：模組 05 §3「草稿｜儲存」前置只寫「項目開放」，拒絕碼列 `ITEM_NOT_OPEN` 而無 `DEADLINE_PASSED`；「項目開放」是否含「未截止」未明寫。本稿依「開放與截止」守門把截止後儲存也回 `DEADLINE_PASSED`（P07 步驟 2 截止後頁面無送出按鈕，草稿是否仍可存未寫）。
- **路由字串**：S05 卡與 S07 卡用 `/dashboard/student/items`、`/items/[id]`、`/dashboard/student/my-submissions`；模組 05 §7 只寫「作業區、內容頁、繳交歷史」沒有路由；原型是 `/dashboard/student/affairs/[id]`；`/items/[id]` 不在 `/dashboard` 下，個人（S05）與組別（S07）共用同一路由。契約 03 §2 路由矩陣是否需列 `/items/[id]` 未查到。需 Roy 定路由。
- **`hasAnyResponse` 的歸屬**：S04 票草稿把 `SubmissionQuery.hasAnyResponse` 介面留在 S04-05（恆 false）、真實作交 S05；S05 卡「schema／API」沒有列 `hasAnyResponse`，模組 04 §5 把它列在 `ItemQuery`、模組 05 §5 列在 `SubmissionQuery`，兩份 spec 同名方法歸不同 port。本稿在 S05-05 換真實作並同時滿足兩個 port，請確認歸屬與 S05 卡是否補列。
- **「Roy 看的畫面」**：S05 卡「出場條件」只有三項（自動測試、操作起點、Fable review），沒有 Roy 畫面；總圖出場四項之（4）「卡上註明的 Roy 看畫面」對 S05 為空；產品模組 05 §10 差距表卻寫「正式版新做名單頁與免填，Roy 屆時看（SUB-02、21、22）」。建議 S05 卡補「Roy 看名單頁與完成率」。
- **`ITEM_NOT_OPEN` 的開放判定**：同 S04 票草稿問題清單：`opens_at` 可設未來（P07 步驟 7 FINAL1），此時 `actual_opened_at` 是「發布時間」；開放判定應用 `COALESCE(opens_at, actual_opened_at)`，模組 04 §2「發布即開放」需補這句。
- **帳本 `operation_kind` 命名**：契約 01 §8 只給 `account.issue_temp_password` 例；`saveDraft`／`submit` 的 kind 字串（例如 `submission.save_draft`、`submission.submit`）沒有清單，各切片可能各取各名（S03 票草稿已提事件型別同類問題）。
- **`EXEMPTED` 的先後**：模組 05 §2 授權層列 `EXEMPTED`，但免填的寫入在 S08；S05 只能以 SQL 設旗標驗證。S05 卡「免填只驗分母顯示」與此一致，只提醒 review 時不要把 S05 的 `EXEMPTED` 測試當成 SUB-22 證據。
