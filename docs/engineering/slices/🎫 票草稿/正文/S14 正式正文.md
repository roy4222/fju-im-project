# S14 正式正文｜維運：VM 首次設定、Secrets、首次部署、health cron、備份到 R2、還原演練、告警、SOP 實跑

> 本檔是 S14 每張票的「可讀正文層」，票號、順序與 BLOCKED 標記照票草稿；技術九欄由產生器自動附在折疊區，這裡不重貼。本切片環境是校方 VM（staging），票多為「照 SOP 做一遍並留執行紀錄」：由工程（Fable）執行與驗證，Roy 負責提供平台項目（VM、DNS、OAuth、Turnstile、R2、金鑰、GitHub Secrets；清單見 `🚀 部署與維運/00 Roy 前置工作清單`）與親自按下部署，並在 E14 整體展示看部署紀錄、health 回應與備份狀態頁。正文不放任何密碼、token、金鑰；測試帳號只寫角色代號 A1。

### S14-01 [維運] 把校方 VM 第一次設定好：Docker、目錄、防火牆、部署帳號與憑證
- **票型**：operations
- **這張做什麼**：照 SOP 01 把校方給的空 VM 變成可以部署的機器：裝好 Docker、建好 `/srv/fju` 底下的資料與備份目錄、防火牆只開 22／80／443、建一個 `deploy` 帳號給自動部署用、放上 Compose 與 Caddy 設定，先把資料庫與 Caddy 兩個服務跑起來，讓 Caddy 對主站與兩個分支插槽網域自動取得 HTTPS 憑證。工程準備可以重複執行的腳本，Roy 以 sudo 執行；磁碟可用不到 20 GB 就停下來記錄。
- **做到哪裡**：本票交付冪等設定腳本、SSH 設定範本、八個步驟的核對輸出與 SOP 01 執行紀錄一列，並更新「目前進度」的 VM 列。環境變數的值由 S14-02；app 與背景工作啟動由 S14-03；備份工具採容器自帶，由 S14-05。本票目前是「工程基礎」（可在 E01 出場後提前做）。
- **Roy 如何確認**：本票由工程驗證；Roy 提供 VM 的 SSH 與 sudo、請校方開對內 80／443、在 Cloudflare 加三筆 A 記錄（主站、b1、b2），並親自執行腳本。Roy 在 E14 整體展示確認 SOP 01 執行紀錄表有一列「成功」（日期、版本、證據連結），以及 Caddy 日誌裡三個網域都出現「憑證已取得」。Roy 不需要看懂每條命令輸出。
- **誰確認**：工程核對／平台由 Roy 提供（VM、DNS、sudo 執行）。
- **原型畫面**：無原型畫面（維運票，無畫面）。

### S14-02 [維運] 把三組環境變數、Google 登入、Turnstile、映像拉取權限與 GitHub Secrets 填好，先不啟動服務

- **Roy 如何確認**：本票由工程驗證；Roy 提供 Google Cloud 專案與 OAuth 用戶端、Turnstile 設定、三份環境變數的值與密碼、映像拉取用的 PAT、SSH 部署金鑰與 Secrets。Roy 在 E14 整體展示確認 SOP 02 執行紀錄一列「成功」、Google 與 Turnstile 主控台截圖（回呼網址、網域）、`gh secret list` 只列名稱、以及 PAT 到期日有記下來。畫面上不會也不該出現任何秘密值。
- **誰確認**：工程核對／平台由 Roy 提供（Google、Turnstile、Secrets、PAT）。

### S14-03 [維運] Roy 親自按下第一次 staging 部署，並實跑一次回滾
- **票型**：operations
- **這張做什麼**：照 SOP 03 做第一次真部署：Roy 在 GitHub Actions 按 `workflow_dispatch`（或 SSH 執行部署腳本），腳本取鎖、記住前一版、拉映像、跑資料庫升級、啟動 app 與背景工作、依部署階段做健康判定（E02 出場前只看 app 四項、背景工作欄為空並在紀錄註明「有限健康條件」；E02 出場後才加背景工作版本與心跳兩項），然後寫一列部署紀錄。空資料庫第一次要跑 `seed:a1` 建管理員，Roy 登入後改密碼。接著實測停機秒數，並做一次回滾演練（回到前一版、健康判定為前一版）。最後把 CI 的部署工作從「乾跑」改成接 Secrets 的真部署，但不接 push 自動觸發。
- **做到哪裡**：本票交付 CD 工作接線、部署腳本實跑、`seed:a1`、回滾演練、停機窗口量測、SOP 03 執行紀錄。部署腳本本體與乾跑測試 S00-10 已做；health 欄位 S00-08、S02-06 已做；正式切換只在 S14-11 預演。本票目前是「工程基礎」。
- **Roy 如何確認**：本票由工程驗證；Roy 親自 dispatch（部署的核准就是 Roy 按下去），並在第一次部署後用 A1 登入 staging 改密碼。Roy 在 E14 整體展示確認：Actions 有三次執行紀錄（乾跑、真部署、回滾）都是綠燈；`deploy_log` 有成功部署與回滾各一列並記明用的健康階段；打開 `/api/health` 看到 200 與版本資訊；停機秒數有實測值。
- **誰確認**：工程核對／平台由 Roy 提供（親自 dispatch、A1 改密、第一次部署時點）。
- **原型畫面**：無原型畫面（維運票，無畫面）。

### S14-04 [維運] 每 5 分鐘自動探測站台健康，連續三次失敗才寄信給 Roy
- **票型**：operations
- **這張做什麼**：GitHub Actions 每 5 分鐘打一次 `/api/health`；回應不是 200 或背景工作心跳超過 5 分鐘沒動，連續三次才算失敗（單次抖動不吵人），失敗由 GitHub 的工作流失敗通知寄信給 Roy。若 Roy 決定設第二通道（例如 Discord webhook），health 失敗、備份失敗、磁碟告警會一起送到那裡；沒設就只有站內。另有一支每日統計 Caddy 存取日誌 5xx 比率超過 1% 就通知的腳本。最後故意打錯網址一次，證明通知真的會到。
- **做到哪裡**：本票交付 health cron 工作流（含連續計數）、共用的 webhook 發送小函式、5xx 統計腳本與排程、SOP 05 步驟 1、3、4 的執行紀錄。站內通知由 S12-15、S12-10；磁碟量測由 S14-07；備份失敗的產生由 S14-06。本票目前是「工程基礎」。
- **Roy 如何確認**：本票由工程驗證；Roy 在 GitHub 通知設定選「只通知失敗的工作流」，並決定要不要設第二通道。Roy 在 E14 整體展示確認：Actions 裡 health cron 連續多次綠燈；有一封「故意失敗」的通知信截圖與隨後恢復的綠燈；若設了 webhook，頻道裡有一則對應訊息。
- **誰確認**：工程核對／平台由 Roy 提供（GitHub 通知設定、第二通道決定）。
- **原型畫面**：無原型畫面（維運票，無畫面）。

### S14-05 [模組10 檔案與服務維運] 做出備份程式：匯出資料庫、加密、上傳到 R2、寫一筆備份紀錄
- **票型**：foundation
- **這張做什麼**：工程做一個 `backup` 服務映像，裡面自帶資料庫匯出、age 加密、rclone 上傳三個工具（`--check` 會印出三個版本）。跑一次就會：用備份專用的資料庫角色匯出、對每把公鑰加密、上傳到 R2 的 `fju-db-backup` bucket（物件鍵含日期與時間）、然後寫一筆「備份紀錄」（成功或失敗、大小、耗時、物件鍵、公鑰數；錯誤訊息裡不含任何 token）。本機備份只留 7 天；任一步失敗就寫失敗列並以非 0 結束；若設了告警 webhook 就發一則。沒有設加密公鑰時直接拒跑，不匯出也不寫紀錄。本機可用 rclone 的本機後端測試，不需要真的 R2。
- **做到哪裡**：本票交付 Dockerfile、備份腳本、`--check`、失敗路徑、webhook 呼叫、本機整合測試（成功一次可解密還原、注入上傳失敗、角色權限、7 天清理、無公鑰拒跑）。VM 上的排程與實跑由 S14-06；站內通知由 S12-15；還原演練由 S14-09。本票目前是「工程基礎」。
- **Roy 如何確認**：本票由工程驗證；Roy 在 E14 整體展示確認 CI 的備份映像 build 綠燈、本機整合測試綠燈，以及工程附的一次本機備份結果（一列成功的備份紀錄、解密後的還原清單摘要）。Roy 不需要操作命令列。
- **誰確認**：工程核對。
- **原型畫面**：無原型畫面（維運票，無畫面）。

### S14-06 [維運] staging 每天凌晨自動備份到 R2，並證明失敗時會通知
- **票型**：operations

### S14-09 [模組10 檔案與服務維運] 從 R2 備份真的還原一次到演練副本，抽查資料並寫一筆演練紀錄
- **票型**：operations
- **這張做什麼**：照 SOP 04「還原演練」在演練副本上做一次：先確認副本沒有掛到正式的資料目錄與資料庫（隔離核對），從 R2 下載最新備份、解密、還原到副本資料庫，用副本啟動 app 抽查：A1 能登入、學生帳號關聯正確、G1 成員、期中收件的版本數與雜湊、評分採計、簽核同意紀錄——主線當時有多少就查多少；在副本裡做一次寫入與一次刪除，再核對正式資料庫的來源樣本雜湊沒變；最後用 `pnpm ops:record-drill` 寫一筆「還原演練紀錄」（備份物件鍵、執行者、隔離核對、抽查表、來源未變、結果、備註），備註必須寫「附件不在此備份範圍」。副本用完銷毀。這是 FIL-05「資料庫備份還原」的證據。
- **做到哪裡**：本票交付 `ops:record-drill` 指令（驗必填、寫不可變列）、演練腳本、一次 VM 演練與報告、SOP 04 執行紀錄。備份產生由 S14-06；副本工具由 S14-08；FIL-05 的最終 PASS 要在 E13 出場後以最終版本再跑一次並由 Codex 核對，不是本票關閉條件。本票目前是「工程基礎」。
