> **2026-09-24 實作回寫**：`POST /sign-up/email` 的失敗回應已統一：Email 已被使用與 Email 格式不對回同一個代碼 `EMAIL_UNAVAILABLE`＋同一句訊息（與註冊頁一字不差），HTTP 狀態由 `wrapper.ts` 外層把套件的 422 統一成 400，不洩漏帳號是否存在。註冊頁（Server Action）仍回契約 02 的 `VALIDATION_FAILED`；工程模組 01 §3 寫的 `USER_EXISTS`，在 HTTP 回應本體實際是 `EMAIL_UNAVAILABLE`。（出處 PR #251）

**內部呼叫辨識**：管理員能力只經 application 用例呼叫伺服器端 `auth.api.banUser／unbanUser／setUserPassword／revokeUserSessions／createUser`。hook 判定「內部呼叫」需兩個條件同時成立：`ctx.request` 不存在（官方 hooks 文件：request「may not exist in server-only endpoints」）**且** composition 的內部包裝器透過 AsyncLocalStorage 設定的 marker 存在。不使用 header。`impersonateUser` 永不呼叫。正反向測試：外部 HTTP 打 `admin/*` 被擋；內部包裝呼叫成功；缺 marker 的伺服器呼叫被擋；停用後撤 session 呼叫失敗仍以業務狀態拒絕並可重試。**（v2.2，D1）**內部能力清單只有上列五個呼叫。模組 01 收斂核對讀 Better Auth 的 `banned` 不用 `auth.api.listUsers`，而是 `fju_app` 對 `users` 套件欄（契約 01 §4.1）的唯讀 SELECT——沒有 session、沒有 request、不經 admin API；`/admin/list-users` 與其他 `/admin/*` 對任何 session（含管理員）維持封鎖，不為 worker 擴放。釘版測試（S01）：外部 HTTP `POST /api/auth/admin/list-users` 帶管理員 session 仍被擋；`readBanned` 在無 request context 下可讀，且在內部包裝 `banUser` 回傳後立即為 true、`unbanUser` 後為 false；安裝後核對 admin plugin 產生的欄名。

**2026-09-15 安裝後補充（better-auth 1.7.5，S01-03／#46）**：admin plugin 的每個 `/admin/*` 端點前面掛著自己的 `adminMiddleware`，它呼叫 `getAuthoritativeSessionFromCtx(ctx)`，**沒有 role 是 admin 的 session 就直接 401**。所以內部包裝器的五個呼叫都必須把「發動這個動作的管理員」的 `headers` 傳進去；marker 管的是「這條路只能從包裝器走」，套件的 middleware 管的是「誰有資格做」，兩個檢查疊加、互不取代（已有測試：帶一般使用者 session 經包裝器呼叫 `banUser` 仍被套件擋下）。**待決**：模組 01 的 `SessionRevocationExecutor` 由 worker 週期執行時沒有任何 session，這幾個呼叫要用什麼身分尚未定案，留給 S02 的 worker 票決定（選項：服務帳號的 session、或該處改用不經 admin plugin 的等價寫入）。本切片的用例都是管理員親自發動，不受影響。

> **2026-09-24 實作回寫**：上段「待決」已定為**不經 admin plugin 的等價寫入**。背景工作（worker）撤銷／恢復 session 時沒有管理員 session，不呼叫 `banUser`／`unbanUser`，改由 `SqlBanStateGateway` 照 better-auth 1.7.5 `plugins/admin/routes.mjs` 逐欄做同樣的事：封鎖寫 `banned=true`、`ban_reason`、`ban_expires=NULL`、`updated_at`，再刪這個人全部 `sessions` 列（本專案沒開 secondary storage 與 cookie 快取，刪列即撤銷）；解除封鎖則三欄清空。代價：`users` 的 banned 三欄原本只由套件寫（契約 01 §4.1），現在 worker 也直接寫；**升級 better-auth 時必須重新核對這段等價性**。管理員親自發動的用例仍走內部包裝器的五個呼叫，不變。（出處 PR #252）

## 3. 身分核實、連結、停用、強制改密、一次性秘密（回覆 R04）

- 核准與臨時密碼必選核實方式（`id_document`／`school_channel`／`other`＋說明），理由與操作者、真實時間由系統存；班代確認不能單獨作依據。
- 連結另一登入方式只在 active 且 fresh session；Google 身分已綁他人拒絕；`disableImplicitLinking=true`。

**2026-09-16 覆核結果（better-auth 1.7.5，S01-02）**：上表「fresh 要求」原本寫「`freshAge` 設 10 分鐘，安裝時驗證此選項存在於 session 設定」——**驗「選項存在」並不等於它會生效**。安裝版本的 `dist/api/routes/session.mjs` 裡，只有 `/list-sessions` 掛 `freshSessionMiddleware`；`/link-social` 與 `/list-accounts` 掛的是一般的 `sessionMiddleware`，`freshAge` 對它們不會被讀到。實測：把 `sessions.created_at` 回推 11 分鐘，`GET /list-accounts` 仍回 200。**改由路由矩陣（`route-matrix.ts` 的 `fresh` 欄）宣告、`hooks.before` 自己比對 `session.created_at`**，判準與套件那支一致（`now - created_at >= freshAge` 即拒絕），回 403 `FRESH_SESSION_REQUIRED`。本表的要求不變，變的是「靠什麼保證」。

> **2026-09-24 實作回寫**：Google 登入加固：（1）`/sign-in/social`、`/link-social` 的請求體帶 `idToken` 一律在 `hooks.before` 回 400 `ID_TOKEN_NOT_SUPPORTED`，只接受 state＋PKCE 的授權碼流程（state、PKCE 由 Better Auth 做）；沒有瀏覽器 state cookie 的回呼連結不建帳號、不登入。（2）預授權老師首次 Google 登入的綁定例外（產品模組 01 §2.3）只在讀到這一趟 OAuth state、且確定是登入而非連結時才可能發生；state 讀不到（null、例外、非物件）一律不綁。（3）連結時 Google Email 必須等於登入 Email（`allowDifferentEmails: false`；產品規則待確認，見產品模組 01 §2.3）。（出處 PR #251、#257）

- 停用：`banUser` 撤全部 session；hook 與 ActorResolver 以 `users.status` 為準；`cookieCache` 關閉。

> **2026-09-25 實作回寫**：session 列改在停用與恢復的**業務交易內**刪除（`delete from sessions where user_id=…`），commit 後的 `banUser`／`session_revocations` 只負責補 `banned`，刪 session 那一步成為冪等的第二層。原因：只靠 commit 後的 `banUser` 時，那一步失敗、逾時或被 worker 認領，停用前的 session 列會留著，恢復一把 `status` 改回 active 就直接復活（沒重新登入就是登入狀態）。恢復時也刪一次，清掉停用 commit 前剛好登入成功的漏網列；恢復後一律要重新登入。被拒的登入本身不留列、不設 cookie（`session.create.before` 回 false 時套件不寫入）。（出處 PR #302）
- 強制改密：`must_change_password=true` 只放行改密與登出；受限 session 可重新登入完成改密。
- 一次性秘密：臨時密碼只在 `SecretOnce` 回應本體；帳本、audit、log、fingerprint、trace 不含原始密碼；重播回「已核發，無法取回」；回應遺失走重新核發，舊密碼失效；測試掃描 DB、log、trace 都無秘密。

## 4. 直接請求與最小揭露

uuidv7 不可猜但不當授權；每用例重驗；跨組讀取統一回「無法存取」；學生頁面、API、匯出、嵌入資料以 HTML 與 JSON 掃描證明無成績評語（GRD-11）；通知列只存 ID 與標題；日誌遮罩密碼、token、cookie、附件、個人回答正文。

## 5. 輸入、HTML、上傳、匯出（回覆 R17 CSV）

- Zod 驗證；富文字 `sanitize-html` 白名單後存，輸出再逃逸。
- 上傳：副檔名白名單、宣告 MIME、magic bytes、大小、系統產生的 storage key；ZIP 只存不解壓；下載 `nosniff`、`attachment`。
- 匯入：UTF-8、固定欄位、每列長度上限。
- **匯出**：主要格式 XLSX，所有儲存格以文字型別寫入（不解析公式）；CSV 對以 `= + - @ \t \r` 開頭的儲存格加 `'` 前綴並以雙引號包裹、內部雙引號加倍；文件寫明 Excel 開啟行為；測試公式字首、分隔符、換行、引號與存檔重開。
- 海報等圖片檔的個資檢查是**人工核閱**（記核閱者、時間、版本、checksum；換檔重核），文字欄位才用正則。

## 6. CSRF、Cookie、CSP、限速（回覆 R17 CSP）

- Server Actions 由 Next 內建 Origin 檢查；Route Handler POST 檢查 `Origin`／`Sec-Fetch-Site`；cookie `secure; httpOnly; sameSite=lax`。
- CSP：依 Roy 對母 spec §4.15 的決定；預設方案 A（動態渲染＋nonce＋`strict-dynamic`）：`default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…'; img-src 'self' blob: data: https://i.ytimg.com; frame-src https://www.youtube.com https://challenges.cloudflare.com; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`；驗證 hydration 正常且注入腳本被擋。

> **2026-09-24 實作回寫**：`form-action` 已改為 `'self' https://accounts.google.com`。登入、註冊、連結的 Google 按鈕是表單送出後轉址到 Google，少了這條時（尤其沒有 JavaScript）瀏覽器會擋下轉址；其餘指令不變。（出處 PR #251）

- 限速（app 記憶體＋Caddy）：登入 10 次／10 分鐘／IP＋帳號；註冊 ~~5 次~~ **30 次**／小時／IP（2026-09-23 Roy 定案：可能全班共用對外 IP，且註冊都需人工核准）；改密 5 次／小時；上傳 20 次／10 分鐘／使用者；~~連續登入失敗 5 次後要求 Turnstile~~（2026-09-23 拿掉：人機驗證不做、只保留限速，#58 後續／不做；§2 表中「達門檻需 Turnstile」與 §7 同樣不再適用，原文保留。總表見 [05 執行手冊](</Users/lubaiyu/Documents/roy422的人生online/專案/🌐 網站與互動/📁 輔大資管系專題網站/🛠️ 工程開發/🧱 實作切片/05 執行手冊.md>) §6 C12、C13）。

**2026-09-16 覆核補充（S01-05）**：Better Auth 自己也有一層限速，它的鍵是 `createRateLimitKey(ip, path)`——**永遠不含帳號**，所以那一層在結構上就做不到本節要的「IP＋帳號」。同一個對外 IP 後面，別人失敗會算到你頭上；全系共用一個校園出口時，這等於任何人都能癱瘓掉全系的登入（實測：60 個不同帳號各錯一次之後，第 61 個人拿正確密碼回 429）。處理方式：

- `/sign-in/email`、`/change-password`：**關掉套件那一層**（`rateLimit.customRules` 給 `false`），門檻一律由 app 記憶體那一份做——登入以 IP＋帳號為鍵，改密以 userId 為鍵。改密同樣不能用 IP 桶：系辦發臨時密碼後一整批人在同一個出口改密是正常流程。
- 本節把粗粒度那一層明寫成「app 記憶體＋**Caddy**」，跨帳號的 DoS 防護因此落在反向代理，不在應用層。
- **待決**：`/sign-up/email` 目前仍用套件的 IP 桶，門檻是 30 次／小時而不是本節寫的 5 次／小時。註冊流程是 S01-09 的票，這一批沒有做，現在收緊會擋到還沒實作的流程。S01-09 要一併決定「5 次／小時／IP」在共用校園出口下是否可行——照字面實作，同一個出口的第 6 位同學就註冊不了。

> **2026-09-24 實作回寫**：限速新增兩條，都用 app 記憶體的 `sharedRateLimiter`，頁面（Server Action）與直接打 API 共用同一個桶：（1）Google 登入 `/sign-in/social` **每 IP 每小時 120 次**（`RATE_LIMITS.signInSocial`；IP 取自 Caddy 覆寫的 `X-Real-IP`）。Better Auth 對 `/sign-in/social` 內建的「3 次／10 秒／IP」已關閉（`customRules` 給 `false`），理由同上：這一步只產生 state 與授權網址、不驗帳密，全系共用校園出口時第四位同學就會吃 429；門檻取 120 而非註冊的 30，是因為 Google 登入每天都用、一間電腦教室五六十人共用一個 IP。（2）待審學生修改申請（`reviseMine`）**每人每小時 20 次**（以使用者為鍵）。這兩個數字由實作者訂定，PR 已列待 Roy 確認。註冊 30 次／小時／IP 見上方 2026-09-23 定案。（出處 PR #250、#251、#257）

## 7. Turnstile 伺服器驗證（回覆 R11）

- 門檻由伺服器計數（登入失敗次數、註冊速率）；達門檻的路由在後端要求 token。
- 後端以 secret 呼叫 siteverify，比對 `success`、`action`（`login`／`register`）、`hostname`；token 有效 5 分鐘且只能用一次。
- 缺、無效、重播、過期 → `TURNSTILE_REQUIRED`；siteverify 網路故障 → fail closed（拒絕並提示稍後再試）；未達門檻的正常登入不要求。
- 測試：直接 POST 不經 widget、缺 token、隨機 token、重播、過期、服務故障。

## 8. 機密、依賴、稽核

機密只在 VM `.env`（三組憑證：owner、app、backup）與 GitHub Secrets；映像不含機密；Dependabot 每週、`pnpm audit --audit-level=high` 阻擋；`audit_events` append-only 且 UI 只讀。
