## 1. 驗收方式

### 1.1 一句話

Codex 用同一個測試屆別、同一批帳號、組別與資料，扮演管理員、學生、老師，按業務順序從開學操作到專題結束並封存；每個階段消費前一階段實際產生的資料。

### 1.2 五個原則

1. **資料連續**：不在階段間換假資料，不直接寫資料庫完成業務。技術查證只用來佐證畫面。
2. **獨立身分**：每個帳號用獨立瀏覽器 profile 或明確登出再登入，登入後核對右上角顯示的姓名與角色再操作。同一瀏覽器不同分頁不算隔離。
3. **明列案例保證覆蓋，探索式操作補漏**：先跑案例 ID，再依畫面繼續嘗試離開回來、重複送出、舊頁面操作、換入口等；探索發現另立缺陷，不改案例的預期。
4. **證據**：每案至少一張關鍵畫面截圖或回執文字；涉及保存的案例加重整或重新登入後的第二張；涉及授權的案例加被拒畫面。
5. **判定四態**：通過、失敗、阻塞、未測。失敗會影響後續步驟時標「依賴阻塞」，可用另存資料集繼續查其他功能，但旅程整體不算通過。

### 1.3 四種驗證層

| 層 | 做什麼 | 不做什麼 |
|---|---|---|
| A 介面操作 | 登入、點按、輸入、上傳下載、對話框、表格；重整、返回、重新登入後再確認；桌機與窄螢幕 | 不綁滑鼠座標，Codex 讀畫面決定操作 |
| B 三角色交叉 | 發布後換學生看；學生甲送出後換乙看同版本；老師看後管理員核對回執、版本、完成率；用他組、他師、未授權帳號確認被拒 | 不用原型角色切換 |
| C 探索 | 填到一半離開、重複送出、舊頁面操作已變更資料、改組員或期限後看其他頁、上傳不合法檔、空狀態與無權限提示、不同入口同一件事 | 不因探索改案例預期 |
| D 技術證據 | 查 log、資料表、產出檔案、API 回應、跑自動測試 | 不用寫 DB 代替操作 |

精準同時請求、計算邊界、交易與大量回歸由自動測試補強，Computer Use 不取代。

### 1.4 Codex 五個參與時機

1. 開發前 review spec：需求遺漏、矛盾、案例能否執行、跨模組契約。
2. 每個切片完成：自動測試加真實操作，核對保存、權限、跨角色狀態；只跑該切片覆蓋的案例 ID。
3. 完整專題流程演練：本文件第 2 節主線加第 3 節例外，一次跑完。
4. 外部整合與部署：Google 登入、日曆實際訂閱、Email 送達、VM 重啟、備份還原各自獨立驗證，不由主線推定。密碼登入不證明 Google 登入；outbox 不證明送達；.ics 產生不證明訂閱更新；DB 還原不證明附件與整站恢復。
5. Roy 本人：UI、閱讀感受、直覺性、是否開放。Codex 的檢查協助找問題，不能代替。

Google 真人驗證、MFA 或外部服務限制若阻擋，記錄阻塞與需要的協助。

### 1.5 業務日期

真正依賴日期的步驟只有六種：開放前不能填、截止前可送、截止後被拒、重開後指定對象可再送、階段或活動日期改變後時間軸與日曆更新、日期經過不代表本組完成。註冊、成組、發布、評分、簽核不需要推日期。主線劇本在需要的步驟標「模擬日期」，其餘沿用上一個值。推進方法在第 6.4 節。

## 5. 範例：05 個人與組別繳交

### 5.1 產品規則（節錄，模組檔第 4 節格式）

來源：§4.6、§22 Q7、§22.2。

| 狀態 | 學生（對象內） | 學生（對象外或他組） | 老師（指導） | 管理員 |
|---|---|---|---|---|
| 未開放 | 看到項目與開放日，不能填 | 看不到 | 看到項目 | 編輯項目 |
| 開放中，無草稿 | 建立草稿 | 拒 | 看狀態「未開始」 | 看完成率 |
| 開放中，有草稿 | 編輯、儲存、正式送出 | 拒 | 看狀態「草稿中」，不看內容 | 看狀態 |
| 已送出（截止前） | 看最新版與歷史，可重送 | 拒 | 看最新版與歷史 | 看最新版、歷史、完成率 |

規則：收件單位是個人時，回答主體是學生本人，不要求成組；是組別時，同組成員共用一份草稿，任一人送出即全組完成。每次正式送出是不可變版本，記送出者、時間、欄位版本、檔案版本；預設顯示最新版。截止後鎖定；重開只對指定對象，必填理由與新期限，不刪舊版。並發以樂觀鎖處理，衝突要提示不可無聲覆蓋。送出必有回執。

待確認：個人收件重送是否與組別相同；完成率分母是否含晚加入者；對象變更後被移出者的回答如何顯示。

### 5.3 工程設計（工程區模組實作設計，節錄）

- 資料：`responses`（id、item_id、schema_version_id、subject_type 個人或組別、subject_id、draft_json、draft_version 樂觀鎖、updated_by、updated_at）；`submission_versions`（id、response_id、seq、submitted_by、submitted_at、schema_version_id、answers_json 不可變、file_ids）；`reopen_grants`（item_id、subject_id、until、reason、granted_by）。唯一約束：一個 item 對一個 subject 只有一筆 response；seq 在 response 內遞增。
- use case：`saveDraft`（檢查對象與成員、開放期間或重開、樂觀鎖版本比對，衝突回 409）；`submitResponse`（同檢查、交易內建立版本並複製答案快照、寫 audit、發通知事件；重複請求以 idempotency key 去重）；`reopenForSubject`（管理員、必填理由與期限、寫 grant 與 audit、通知指定對象）。
- 授權在 use case，以操作者、屆別、對象成員關係判斷；畫面隱藏不算。
- 截止判斷用 Clock port 的業務日期；比較截止時刻與重開期限。
- 覆蓋案例：SUB-01 到 SUB-18。
