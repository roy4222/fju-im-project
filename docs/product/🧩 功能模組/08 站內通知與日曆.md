### 誰、什麼時候、從哪裡進來
三個角色都有右上角的鈴鐺與「通知」頁。系辦發公告、發收件、改截止、重開、輪到某人同意時，相關的人會收到站內通知；徽章顯示未讀數，讀過就消。站內日曆在學生首頁：作業截止自動來自收件項目，說明會這類活動由系辦另外加。本輪不寄 Email、不做 Google 日曆或外部訂閱。

### 一步一步怎麼操作
1. 學生進「通知」：依類型標籤（截止、簽核、繳交、系統）列出每則的標題、說明與時間，可「全部標為已讀」，未讀數在鈴鐺上。
2. 老師的通知匣有「待評分」「等待老師同意」「某組送出」「產學組尚未指派」；系辦的有「帳號等待審核」「逾期組別」「缺評老師」「每日備份完成」。
3. 學生首頁的「專題行事曆」是當月月曆，點日期看當天，圖例分截止、活動、競賽；「接下來」列本週與之後的截止與活動。
4. 系辦改截止或活動日期，站內日曆與通知更新同一個事件，不會多出一筆。

### 操作後自己與其他角色看到什麼
收到通知的人：鈴鐺數字與通知匣變；點通知連到來源項目，正式版每次重新驗權限。沒在對象內的人不會收到。系辦：可在發布或修改時選是否通知。

## 4. 產品規則
### 本輪交付通道
站內通知與站內日曆完整保留。Email 寄送、Google Calendar 及外部 .ics 訂閱整合延後，不列本輪試用或目前正式 Gate。先前「.ics 保留」被 2026-09-11 Roy 最新指示的外部日曆延後範圍取代；恢復時重新確認產品邊界。Google OAuth 登入不是日曆整合，仍屬 ACC 模組。

### 已定事件
重要公告發布、新收件發布、期限異動、退回／指定重開、等待本人同意，依事件的適用受眾建立站內通知。一般小幅編輯由管理員選擇是否通知。

### 事件矩陣（2026-09-12 定案 Q-NTF01，含前五輪新增事件）

| 事件 | 收件人 | 規則 |
|---|---|---|
| 重要公告發布 | 受眾 | 已定 |
| 新收件發布 | 收件名單成員：個人收件通知本人，組別收件展開通知該組有效成員 | 已定；組別新增成員時只補新成員適用的通知，不重發全組 |
| 加入收件名單（截止前自動或管理員明確加入） | 該人 | 與發布時同一種「新收件」通知；原回答仍有效時顯示「已加入，目前已完成」，不叫人重填。截止後「加入名單＋指定重開」若是一次確認的操作，發一則完整通知說明已加入與新期限；分開發生則各留事件 |
| 移出收件名單 | 本人 | 只給本人必要說明，不向其他學生透露處理理由 |
| 免填／恢復應填 | 本人 | 各一則；恢復時若已截止不能顯示可立即填交，仍依指定重開規則 |
| 期限異動 | 受影響者 | 已定 |
| 退回／指定重開 | 個人收件通知本人；組別收件通知該組 | 已定；其他人不收 |
| 正式送出版本 | 其他有效組員 | 每次正式送出一則；暫存不通知；老師不收 |
| 等待本人同意（分組邀請、簽核輪到本人） | 本人 | 已定 |
| 提案終止 | 提案人與全部被邀請者，按使用者去重 | 帶終止類型；管理員內部備註不複製給所有人 |
| 組別成立 | 成立後全員 | 一則 |
| 成員加入／移出 | 異動前後成員的聯集與目前主指導 | 被移出者只取得本人異動說明，不因此重新取得組別內容 |
| 組長更換 | 全組 | 清楚列出新組長 |
| 組別解散 | 解散前有效成員、主指導、評分工作因此停止的老師 | 一則 |
| 指導指派／認領 | 該組全員與新老師 | 已定；重派另通知原老師 |
| 合作案解除／換案 | 受影響的組員與案主 | 已定 |
| 評分指派 | 新增、替換通知需要評分的新老師；解除通知原老師 | 依模組 06 的實際採計選擇；「保留已完成評分」不產生虛構的補評通知 |
| 評分退回 | 仍有權處理該筆評分的老師 | 附可見理由與入口；原老師已失去指派或停用時先由管理員處理指派，不產生無法完成的補評要求 |
| 最終結果更正完成 | 不通知 | 管理員自己的動作 |
| 更正進入待復核 | 有處理權的管理員 | 首次進入時通知，管理端保留待辦；未解決不反覆提醒；任一管理員處理後其他人點開看到已處理；個人已讀與共同待辦分開 |
| 簽核完成 | 完成當下的有效參與成員與主指導，每人一則 | 以「組別＋簽核版本」為單位；文案「此版本站內簽核已完成」，不代表校方採認；後來產生新版時舊通知標示為歷史版本的完成紀錄 |
| 帳號審核結果 | 不進通知匣 | 待審者可登入看等待審核頁，重新載入或重新登入顯示最新狀態、退回理由與下一步；不出現「請等通知信」；Email 恢復後另定 |
| 帳號等待審核 | 不做通知 | 管理首頁即時待辦計數，連到待審清單 |
| 收件逾期 | 管理員 | 有逾期未完成者才發，按屆別、收件項目、期限版本彙整；逾期看各收件者實際有效期限，排除免填與移出，指定重開期限內不算；重開到期也檢查。彙整保留產生當時的數量與時間，點開顯示目前處理狀態 |
| 產學組尚未指派 | 該屆有認領資格的有效老師，管理員也收一則 | 成組期結束時仍有未指派組才發 |

| 缺評老師 | 不做通知 | 管理待辦與缺評清單 |
| 備份 | 成功不通知；失敗通知管理員 | 全站維運事件，用真實時間（模組 10） |
| 封存／解封 | 不另發通知 | 進入該屆時明確顯示目前狀態；解封後的指定重開或新版簽核照各自事件通知 |
| 小幅修改 | 管理員選擇 | 已定 |

> **2026-09-24 實作回寫**：（1）新增事件 `ops.worker_alert`（背景工作告警）：投影或到期工作失敗達 5 次標為失敗等情況時發出，收件人是當下所有啟用中的管理員（有效管理員角色且帳號啟用），與「備份失敗通知管理員」同類；通知只存標題，沒有管理員時不會卡住重試。（2）公開、或對所有登入者發布的公告不逐人寫通知，只留事件。（出處 PR #252、#256）

### 去重、補建與保存（2026-09-12 定案）
每次真正成功的業務變更產生固定事件 ID，來源、屆別、類型與版本記在事件內；通知以「事件 ID＋收件人」去重，同一人兼具多個收件身分仍只收一則。同一版本收件的「免填→恢復應填→再次免填」是三個事件，重試同一次免填才算重複。收件人依事件發生時確定，補建通知不能重新展開成另一批人。業務變更成功後若通知建立失敗，系統可補建，不要求使用者重做業務操作；只有通知真正出現在適用帳號的通知匣，才算通知驗證完成。通知永久保留、不自動清除。

### 舊通知與失權（2026-09-12 定案）
舊通知一律保留不刪。重新驗權包含通知本身：列表、摘要與回應資料都不能繼續露出已失權的私有內容，只保存必要的事件紀錄。狀態要分清：失權顯示「此項目目前無法存取」；來源已撤回顯示「來源已撤回」；已封存依歷史閱覽權進入唯讀畫面。本人被移出、被解除指派的通知仍保留必要的本人異動說明。

### 通知匣（2026-09-12 定案）
預設顯示本人所有屆別及全站通知，依時間排序，提供屆別篩選，不能只顯示最新一屆。屆別封存後個人仍可把舊通知標為已讀；已讀跨登入保存，不等於業務完成。

### 通知內容及操作
通知能辨識來源項目、事件、時間及下一步。已讀狀態屬個人，徽章依未讀計算；讀通知不等於完成收件或簽核。來源連結每次重新驗權限，不能用過期通知取得已失去資格的資料。相同動作重試不能造成重複通知；保存與重試方式由工程設計。

### 站內日曆
作業截止由專題事務項目衍生，獨立活動由管理員維護。來源改期要反映同一事件；取消要有清楚狀態。可見範圍跟來源一致，訪客不能看到私有截止。指定 G3 重開只讓 G3 看有效期限，不能把全體截止改成 G3 的新期限。
工程可保留通道 port／outbox 擴充點，但 outbox 不是寄達證據，也不是新增前台功能。

## 5. 狀態與權限
事件→站內未讀→已讀；來源仍獨立有自己的完成狀態；失權／撤回／封存三種狀態分別顯示；待復核類的共同待辦與個人已讀分開；外部通道延後。

## 6. 欄位與資料歸屬
事件 ID、來源 ID、屆別、事件類型、版本、發生時的收件人集合、標題時間連結、個人已讀、彙整通知的產生時數量與時間；活動／截止來源。

## 7. 保存、版本與回執
已讀跨登入保存；以事件 ID＋收件人去重，重試不重複；通知建立失敗可補建；不以 outbox 當送達證據。

## 8. 其他角色所見
