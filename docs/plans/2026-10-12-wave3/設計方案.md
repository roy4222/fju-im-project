## 2. 「刪除」的資料層（Q17、Q28）

**語意（定案）**：撤回＝已發布、沒人回覆 → 回草稿（已有）；下架＝前台看不到、後台還在、可重新發布（已有）；**刪除＝只限草稿與已下架；後台清單也看不到；記稽核；已寄通知不收回；不能恢復**。Q28：收件項目只要有任何回答（存過草稿或正式送出，沿用撤回用的 `hasAnyResponse`）就不能刪，只能下架。

**做法：刪除標記，不實體刪列。** 理由：
- `managed_items` 在權限矩陣是 `"delete": false`（`infrastructure/db/permissions/matrix.json:44`），六張子表外鍵全是 `restrict`（`infrastructure/db/schema/items.ts:163,175,196,216,232,265`）；`showcase_entries` 也是「不刪列」（matrix.json:72-74、`drizzle/0010_s11_signoff_showcase.sql:199-222`）、`showcase_versions` 有觸發器擋刪改。實體刪除要改權限又要連鎖刪稽核依附資料，風險大。
- **不新增 status 值**：`managed_items` 有多條 `status = 'draft' or …` 的 CHECK（items.ts:125,132），草稿收件被刪時若把 status 改成 `deleted` 會撞約束；保留原 status、另加欄位最穩。
- 研究建議 2「`deleted_at／deleted_by`，不提供恢復 API、稽核另記」與定案一致，採用。

**欄位**（W0 一次加，migration `0012_wave3_delete_home`）：

| 表 | 新欄位 | 約束 |
|---|---|---|
| `managed_items` | `deleted_at timestamptz null`、`deleted_by_user_id text null`（型別同 `updated_by_user_id`） | `managed_items_deleted_check`: `deleted_at is null or status in ('draft','archived')`；兩欄同時有或同時無 |
| `showcase_entries` | 同上兩欄 | `deleted_at is null or status in ('draft','withdrawn')`；app 角色欄位級 UPDATE 授權補上這兩欄與 `home_position`、`status`、`award_level`、`award_label`、`current_version_id`（0010:199-222 只給部分欄位，實作時照原寫法補 grant） |
| `showcase_entries` | `home_position smallint null`（首頁輪播順序，見 §4） | `home_position is null or home_position between 1 and 99` |
| `project_events` | `deleted_at`、`deleted_by_user_id` | `deleted_at is null or status = 'cancelled'` |
| `industry_opportunities` | `deleted_at`、`deleted_by_user_id` | `deleted_at is null or status in ('draft','withdrawn')` |
| 新表 `home_settings`（§3） | — | — |
| 新表 `submission_reopens`（§6-①） | — | — |

**規則（所有內容共用）**：
- 刪除只在「草稿」或「已下架／已取消」時可以；發布中要先撤回或下架。理由：前台曾公開的東西一定先經過「看不到」這一步，誤刪面積最小。
- 被刪的列：一般後台查詢、前台查詢、通知連結開啟、附件下載、檔案管理的「使用此檔案的頁面」全部當作不存在（前台回 404「找不到這個頁面」，不是「已下架」）。
- 稽核：`item.deleted`／`showcase.deleted`／`activity.deleted`／`opportunity.deleted`，payload 存刪除前的 status、標題、屆別（之後只剩稽核看得到）。
- 附件檔案不刪（`file_references` 照留）；檔案管理頁不再列出被刪項目為引用來源（W1 改 `infrastructure/ops/file-list.ts`）。
- 已寄的通知不收回；點開看到 404 頁（T1 的中文 404）。

**前台排除的位置**：公開查詢本來就只看 `status = 'published'`，加上 CHECK 保證被刪的不會是 published，所以前台不用改條件；要改的是「後台與學生端會列出草稿／已下架」的查詢。W1 的硬性清單：`rg -n "from managed_items" web/src/infrastructure` 目前 20 處（pg-items 5、pg-public-items 4、attachment-policy 1、ops/file-list 1、submissions/pg-submissions 5、pg-roster 2、pg-advisor-submissions 2），逐一判斷：列清單或開單筆的加 `and deleted_at is null`（單筆鎖 `#lock` 被刪回「找不到」），只算統計且已限 published 的可不加，並在 PR 說明逐處結論。

## 9. 全站 UX 規則（Q19；採研究報告的 5 條，所有第三波新畫面必須遵守）

1. **永久刪除、重置、結算另設「危險操作」區**（頁面或對話框底部，跟日常按鈕拉開）；確認視窗寫：對象、範圍、後果、能不能恢復。確認鈕寫動作（「刪除這則公告」），不是「確定」。只有不可逆或影響多人的才確認，日常動作不加關卡。
2. **相依設定就地說明**：某個設定決定別處出不出現時，旁邊寫「影響哪裡」並給前往入口（例：榮譽榜位置寫「會出現在前台榮譽榜」；獎項寫「選了才會上優秀專題與首頁」）。
3. **首頁直接進待辦；列表支援「篩選 → 多選 → 批次」**（這次只做批次核准；其他批次不新增）。
4. **沒有結果或不能操作的畫面，說原因＋下一步**：「第一次沒資料」給新增入口；「篩選沒結果」給清除篩選；不能做的動作附原因，不留點了沒反應的入口。
5. **表單單欄分組、標籤常駐、單位寫清楚**；列表預設只留工作必要欄位。
