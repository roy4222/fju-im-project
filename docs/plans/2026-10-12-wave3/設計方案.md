## 2. 「刪除」的資料層（Q17、Q28）

**語意（定案）**：撤回＝已發布、沒人回覆 → 回草稿（已有）；下架＝前台看不到、後台還在、可重新發布（已有）；**刪除＝只限草稿與已下架；後台清單也看不到；記稽核；已寄通知不收回；不能恢復**。Q28：收件項目只要有任何回答（存過草稿或正式送出）就不能刪，只能下架；判斷沿用撤回用的 `SubmissionQuery.hasAnyResponse`（port 在 `application/items/ports.ts:143`，實作 `infrastructure/submissions/pg-response-presence.ts:27`，`pg-items.ts` 生命週期指令第 883 行附近已這樣呼叫）。

**做法：刪除標記，不實體刪列。** 理由：
- `managed_items` 在權限矩陣是 `"delete": false`（`infrastructure/db/permissions/matrix.json:44`），六張子表外鍵全是 `restrict`（`infrastructure/db/schema/items.ts:163,175,196,216,232,265`）；`showcase_entries` 也是「不刪列」（matrix.json:72）、`showcase_versions` 有觸發器擋刪改（`drizzle/0010_s11_signoff_showcase.sql` 末段）。實體刪除要改權限又要連鎖刪稽核依附資料，風險大。
- **不新增 status 值**：`managed_items_status_check` 只認 `draft／published／archived`，另有多條 `status = 'draft' or …` 的 CHECK（`schema/items.ts:110-135`）；若把 status 改成 `deleted` 會撞約束。保留原 status、另加欄位最穩。
- 研究建議 2「`deleted_at／deleted_by`，不提供恢復 API、稽核另記」與定案一致，採用。

**欄位**（W0 一次加，migration `0012_wave3_delete_home`）：

| 表 | 新欄位 | 約束 |
|---|---|---|
| `managed_items` | `deleted_at timestamptz null`、`deleted_by_user_id uuid null references users restrict` | `managed_items_deleted_check`: `(deleted_at is null) = (deleted_by_user_id is null)` 且 `deleted_at is null or status in ('draft','archived')`。矩陣是整列 `update: "all"`，新欄不用補 grant |
| `showcase_entries` | 同上兩欄；`home_position smallint null` | `deleted_at is null or status in ('draft','withdrawn')`；`home_position is null or home_position between 1 and 99`。**這張表是逐欄白名單**（0010 只給 `status, current_version_id, revision, updated_at, updated_by_user_id`，0011 已補 `award_level, award_label`）：W0 在 matrix.json 該列加 `"updateAddedIn": { "W0": ["deleted_at","deleted_by_user_id","home_position"] }`，`update` 陣列改成最後的樣子（保留 `T39` 那組）。**審查修正 1（查證）**：`scripts/generate-grants.mjs:37-38` 的切片→migration 對照表只認 S11、T39，:147 遇到未知切片直接退出，:153-155 又禁止同一切片既有新表權限又有補欄 amendments。所以 **W0 可改 `generate-grants.mjs`**：對照表加 `W0: 'drizzle/0012_wave3_delete_home.sql'`，並讓同一個產生區塊先產生新表（`home_settings`、`submission_reopens`）的權限、再接舊表的補欄 GRANT；歷史 migration 一字不改；產生器自己的測試（若有）補案例，CI `--check` 要過 |
| `project_events` | `deleted_at`、`deleted_by_user_id` | `deleted_at is null or status = 'cancelled'`（狀態值見 `schema/timeline.ts:102`）；矩陣整列 update |
| `industry_opportunities` | `deleted_at`、`deleted_by_user_id` | `deleted_at is null or status in ('draft','withdrawn')`（`schema/advisors.ts:137`）；矩陣整列 update |
| 新表 `home_settings`（§3） | — | 首頁大圖沿用既有 `stored_files.purpose = 'photo'`（CHECK 已有這個值、全站沒人用，`schema/files.ts:52`），**不改 `stored_files_purpose_check`、不加 `file_references` 型別**。**審查修正 1**：`id smallint` 不是 uuid 主鍵，`migrations.integration.test.ts` 用 information_schema 掃欄位型別的斷言會撞到（審查方在 /tmp 重現）；W0 把 `home_settings` 明列為該斷言的例外，並另斷言 `id` 是 smallint、CHECK 只允許 1 |

**規則（所有內容共用）**：
- 刪除只在「草稿」或「已下架／已取消」時可以；發布中要先撤回或下架。理由：前台曾公開的東西一定先經過「看不到」這一步，誤刪面積最小。
- 被刪的列：一般後台查詢、前台查詢、通知連結開啟、附件下載、檔案管理的「使用此檔案的頁面」全部當作不存在（前台回 T1 的中文 404 `app/not-found.tsx`，不是「已下架」）。
- 稽核代碼照既有命名（`item.archived`、`item.withdrawn`、`item.republished` 用過去式）：`item.deleted`／`showcase.deleted`／`activity.deleted`／`opportunity.deleted`，payload 存刪除前的 status、標題、屆別（之後只剩稽核看得到）。
- 附件檔案不刪（`file_references` 照留）；檔案管理頁不再列出被刪項目為引用來源（W1 改 `infrastructure/ops/file-list.ts:49-57` 的 join 條件）。
- **下載授權先排除已刪內容（審查修正 3，查證）**：`infrastructure/items/attachment-policy.ts:26` 與 `infrastructure/showcase/poster-policy.ts:44` 在查項目之前就對管理員回 `true`，只在 SQL 加 `deleted_at is null` 擋不住管理員下載已刪公告的附件與已刪作品的海報。改法（W1 改 attachment-policy、W2 改 poster-policy）：政策一進來先把 `file.references` 過濾成「指向未刪除的項目／條目」的有效引用，沒有任何有效引用就對**所有身分含管理員**拒絕；管理員的提前放行搬到過濾之後。單篇查詢（`open`／`entry`）先判刪除回 404，再判下架回「已下架」頁。
- 已寄的通知不收回；點開看到 404 頁。

**後台與學生端要排除的查詢**：公開查詢本來就只看 `status = 'published'`，加上 CHECK 保證被刪的不會是 published，所以前台不用改條件；要改的是「後台與學生端會列出草稿／已下架」的查詢。W1 的硬性清單：`grep -rn "from managed_items" web/src/infrastructure --include='*.ts' | grep -v test` **共 20 處**（pg-items 5、pg-public-items 4、attachment-policy 1、ops/file-list 1、submissions/pg-submissions 5、pg-roster 2、pg-advisor-submissions 2），逐一判斷：列清單或開單筆的加 `and deleted_at is null`（單筆鎖 `#lock` 被刪回「找不到」），只算統計且已限 published 的可不加，並在 PR 說明逐處結論（表格：檔案、行、加不加、理由）。
