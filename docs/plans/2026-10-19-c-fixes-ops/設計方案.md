## 1. V4：驗證碼頁已驗證時明講、成功後轉址 replace（⑤-01）

### 1.1 現況與根因

- `web/src/app/register/verify/actions.ts:62-64`：`verifyOtpAction` 在 `pendingVerificationEmail()` 回 null（＝這個 session 已經驗證過）時 `redirect('/register/verify')`。驗證頁的 server page 再把已驗證的人導去 `/register/apply`。使用者看到的是「我剛輸入的碼不見了、又回到第 3 步」，不知道發生什麼事。
- `web/src/app/account/actions.ts:124`：`verifyAccountOtpAction` 在 `me.emailVerified` 為真時 `redirect('/account?verified=email')`，輸入錯碼也會被當成成功。`:107` `sendAccountVerifyOtpAction` 同樣靜默導走。
- 根因：驗證成功後 `redirect('/register/apply')` 是 `push`，瀏覽器「上一頁」會回到 client router cache 裡的舊驗證頁（表單還在），再送出就撞到上面兩條靜默轉址。repro 分支 `claude/fix-register-otp` 的 `web/e2e/register-otp-wrong-code.spec.ts` 情境 E（上一頁後送錯碼）、F（兩個分頁）、G（`/account` 舊表單）目前紅。

### 1.2 規格

**V4-a 已驗證時明講（兩處）**

| 位置 | 現在 | 改成 |
|---|---|---|
| `register/verify/actions.ts` `verifyOtpAction`、`resendOtpAction`：`pendingVerificationEmail()` 回 null | `redirect('/register/verify')` | **null 有三種原因，先用本人 session 分辨**（`resolveActor` 只呼叫一次）：(a) 沒有本人有效 session（`actor.kind !== 'authenticated'`）→ 維持 `redirect('/register/verify')`，由 page 導去登入；**未登入絕不能顯示「已驗證」**。(b) 有本人 session 且這個帳號**最新**的 `emailVerified` 為真（以 `viewMine` 回執或既有 me 查詢當下讀到的值為準）→ 回表單狀態 `{ error: '這個 Email 已經驗證，請到第 3 步。', attempt, nextHref: '/register/apply' }`；不轉址；`nextHref` 固定 `/register/apply`，已送件或已開通的人由 page 再導到該去的地方（既有）。(c) 其餘（有 session 但 `emailVerified` 為假，或 `viewMine` 不 ok）→ 維持今日 redirect。**不得以 `homeForUser` 目的地推定 Email 已驗證**：`composition/accounts.ts:247-258` 先判角色，「已核准但沒驗證」的舊帳號 home 是 dashboard，`emailVerified` 卻是假（反例 AC-3b） |
| `register/verify/actions.ts` 續辦（resume ticket）cookie 不在 `:52` | 「這次續辦已經失效（逾時或有更新的驗證信），請回第 1 步重新填一次。」 | cookie 消失有兩種原因，**先用 session 分辨**，不能只看 cookie：(a) 這個瀏覽器已有本人有效 session 且最新 `emailVerified` 為真（同上一列，不看 `homeForUser`；另一分頁剛完成續辦：`completeSignupResume` 刪了 cookie、發了新 session，情境 H）→ 「這個驗證碼已經用過或換過新的；如果你在另一個分頁已經驗證完成，請直接到第 3 步。」＋`nextHref: '/register/apply'`。(b) 其餘——沒有本人 session（真正逾時、cookie 被清、換了瀏覽器），或有 session 但 `emailVerified` 仍為假（沒有完成證據）→ 維持原句（回第 1 步）。前置分別是 AC-5 與 AC-6／AC-6a，互斥 |
| `account/actions.ts` `verifyAccountOtpAction:124` | `redirect('/account?verified=email')` | `failed('這個 Email 已經驗證，不用再輸入驗證碼。', 'ALREADY_VERIFIED')`；頁面重新整理後表單自然消失（既有保證：已驗證的人在 `/account` 看不到「驗證 Email」） |
| `account/actions.ts` `sendAccountVerifyOtpAction:107` | `redirect('/account')` | 同上一句，`code: 'ALREADY_VERIFIED'` |

- `VerifyFormState`（`register/_components/form-data.ts:90`）加選填 `nextHref?: string`；`VerifyForm` 在 `error` 旁渲染 `<a href={nextHref}>到第 3 步</a>`，`role="alert"` 的錯誤行維持既有 testid／結構（repro 的 e2e 以 `getByRole('alert')` 找）。
- `/account` 的 `VerifyEmailForm`：`ErrorLine` 照既有 `AccountFormState.error` 顯示；不新增轉址。
- 訊息是**錯誤行**，不是成功通知：使用者剛才送的碼沒有被接受，不能顯示綠色。
- 判斷順序固定是「本人 session → 最新 `emailVerified` 為真 → 才顯示已驗證句與第 3 步連結」；其餘維持原導向或續辦失效句。`homeForUser` 的目的地不能當成驗證證據。`pendingVerificationEmail()` 回 null 不能直接當成已驗證（它在未登入時也回 null）；實作可把它改成回 `{ kind: 'anonymous' | 'verified' | 'pending', email? }` 的 helper，仍留在 `actions.ts`。

**V4-b 成功後轉址 replace**

- `verifyOtpAction` 成功：`redirect('/register/apply', RedirectType.replace)`（Next 16 `next/navigation` 的 `redirect(url, type)`，文件 `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/redirect.md`）。
- `verifyAccountOtpAction` 成功：`redirect('/account?verified=email', RedirectType.replace)`。
- 效果：驗證成功後按「上一頁」不會回到驗證頁，而是回到驗證頁之前那一頁（第 1 步或登入前的頁）。驗證頁的 server page 本來就把已驗證者導走，所以即使使用者手動輸入 `/register/verify` 也到不了舊表單。
- 不清 client cache、不加 `router.refresh()`：replace 已經把舊項目從歷史裡拿掉，情境 E 的「上一頁」在新版本會落在第 1 步（頁面對已驗證者導去 `/register/apply`），表單不存在，錯碼無從送出。**情境 E 的斷言方向因此改寫**（見驗收案例 AC-2、AC-3 與 §13）。

**不改**：`register/verify/page.tsx` 的導向規則、`login/*`、`reset-password/*`、`register-steps.spec.ts`、`pages.spec.ts`。④ C4-07 的版型票與本票不重疊（契約 X-⑤-1）。

### 1.3 留紅 e2e 的處理

把 repro 分支的 `web/e2e/register-otp-wrong-code.spec.ts` 搬進本票（commit 247915a／a0304dd 的內容，以搬進來的版本為準），保留 A／B／C／E／F／G／H 八個情境，E 與 H 的預期照 §1.2 改寫；全部必須綠。不另外改 `email-verify.spec.ts`（既有保證 AC-VI-50／62／65 預期不動，跑一次證明）。

## 3. S16：公開檔案交給 Cloudflare 快取（⑤-03）

### 3.1 現況

- 大檔（公告附件、資源 PDF、海報）每次下載都從 VM 串流（`/api/files/[id]`），走查 S16 擔心的是頻寬與 VM 負載。Roy 定案：Cloudflare 擋在前面 → 由 Cloudflare 快取解。
- app 現在只有「訪客也拿得到的 PNG／JPEG」回 `public, max-age=300, must-revalidate`＋ETag（`application/ops/files.ts:389` `isCacheableDownload`、`composition/files.ts:145`），其他公開檔一律 `private, no-store`。Cloudflare 尊重來源標頭：`private`／`no-store` 不會進邊緣快取，所以**不改 app，Cloudflare 什麼都快取不到**。
- `/api/files/<uuid>` 沒有副檔名，不在 Cloudflare 預設快取的靜態副檔名清單裡，**必須**加一條 Cache Rule 才會被視為可快取。

### 3.2 規格

**app 端（本票唯一的程式改動）**

- `isCacheableDownload` 改成：`d.publicRead` 為真即可快取，不再看 MIME。理由：`publicRead` 的定義是「訪客走同一條政策也放行」（`files.ts:461`），回應內容對所有人一樣，沒有身分差異，快取不會讓人多看到東西；MIME 限制是 Q62 時「只想快取小圖」的保守選擇，S16 的目標正好相反。
- 標頭維持 `public, max-age=300, must-revalidate`＋ETag（常數名 `PUBLIC_IMAGE_MAX_AGE_SECONDS` 改名 `PUBLIC_FILE_MAX_AGE_SECONDS`，值 300 不變；`composition/files.ts` 跟著改名）。Cloudflare 那條 Cache Rule 的步驟由 ⑤-04 一併寫進 README（§4.4 第 5 步），⑤-03 不碰 README。5 分鐘＝下架、撤回、換檔之後最多 5 分鐘內還能從邊緣拿到舊內容，與今日公開圖片的行為一致（契約 02 §8「授權結果不跨請求快取」指伺服器端，沒變）。
- 加 `s-maxage` 或主動 purge：不做（待問 Q3 有替代方案與理由）。
- 拒絕、導向、`FILE_GONE`、私有檔、頭像：標頭不變（`private, no-store` 或 `private, no-cache`），Cloudflare 一律不存。預覽路由 `/api/files/[id]/preview` 與下載共用 `fileCacheHeaders`，自動一致（AC-A-47 既有保證）。
- 既有 e2e `file-download-pages.spec.ts:431-460`（AC-V21、V35）寫死「公開公告的 PDF 附件不可快取」，那是 Q62 的裁定；S16 定案推翻它。本票改寫 AC-V35 那段：公開 PDF 改成 `expectPublic`（200、`public, max-age=300, must-revalidate`、ETag＝checksum、帶 `If-None-Match` 回 304），下架後帶舊 ETag 仍是 401。頭像、私有檔、草稿海報、「本屆學生」公告附件的 `private, no-store` 斷言不變。`avatar-download.spec.ts` 不改。

**Cloudflare 端（Roy 操作，寫進 `ops/README.md` 的 Cloudflare 段，見 §4.4）**

- Caching → Cache Rules 一條：`URI Path starts with "/api/files/"` → Cache eligibility：Eligible for cache；Edge TTL：**Use cache-control header from origin**（來源沒給可快取標頭就不存）；Browser TTL：Use cache-control header from origin。不要選「Override origin」。
- 不開「Cache Everything」整站規則：HTML 頁都帶 session 判斷，整站快取會把登入者的頁面存給訪客。
- 驗證方式：對一個公開 PDF 連打兩次，第二次回應標頭 `cf-cache-status: HIT`；對一個私有檔（登入後）回應 `cf-cache-status: BYPASS` 或沒有該標頭且狀態 403。

## 4. Cloudflare 代理：真實 IP、SSL、來源限制（⑤-04）

### 4.1 定案與前提

- Roy 定案：Cloudflare DNS 代理（橘雲）擋在 VM 前，**不搬 Workers**、app 與 Caddy 仍在 VM。測試站與正式站兩個主機名都走代理。
- 現況：Caddy（`caddy:2.10-alpine`，`docker-compose.edge.yml:21`）直接面對網際網路，`ops/Caddyfile.vm` 用 `header_up X-Real-IP {remote_host}` 把連線來源 IP 交給 app；app 的登入限速（`sign-in-rate-limit.ts:60`）、登入動作（`login/actions.ts:35`）、Better Auth 限速（`auth-instance.ts:310`）都先讀 `x-real-ip` 再讀 `x-forwarded-for`。Let's Encrypt 用 HTTP-01，Caddy 自己做 http→https 轉址。
- 代理之後若什麼都不改：`{remote_host}` 會變成 Cloudflare 的 IP，所有人共用同一個限速桶，登入幾次全站就被鎖。

### 4.2 Caddy 規格（repo 改動）

- `ops/Caddyfile.vm` 全域選項加：
  - `servers { trusted_proxies static <Cloudflare IPv4 與 IPv6 範圍清單> ; client_ip_headers CF-Connecting-IP }`。清單來源 `https://www.cloudflare.com/ips-v4` 與 `/ips-v6`，寫死在檔內並註明抓取日期；Caddy 2.10 內建沒有 Cloudflare 來源模組，不加第三方插件（不換映像）。
  - 兩個站的 `reverse_proxy` 改 `header_up X-Real-IP {client_ip}`。`{client_ip}` 在來源是受信代理時取 `CF-Connecting-IP`，不是時就是連線 IP，所以**切換橘雲前後都正確**，不必配合 Roy 的切換時間合併。
- 保留 Let's Encrypt HTTP-01：Cloudflare 會把 80 的請求代理到來源 80，Caddy 照常回答挑戰。前提是 Cloudflare **不要**開「Always Use HTTPS」與「Automatic HTTPS Rewrites」，轉址交給 Caddy（見 §4.4 清單）。
- 不改 `docker-compose.edge.yml`（映像不換、port 不變）。
- 來源限制（只讓 Cloudflare 連到 80／443）：**不能用 ufw**。Caddy 的 80／443 是 Docker 發布埠（`docker-compose.edge.yml:24-27`），封包走 FORWARD 鏈、不經 ufw 的 INPUT 規則（`ops/vm-setup.sh:206` 已註明；Docker 官方「Packet filtering and firewalls」），ufw 規則寫了也擋不到，AC-26 不會成立。新腳本 `ops/cloudflare-origin-lock.sh` 改在 Docker 保留給管理員的 **`DOCKER-USER` 鏈**掛轉送規則，與 VM 的 Docker 同一個 iptables 後端（Ubuntu 的 `iptables`／`ip6tables`，nft 或 legacy 後端指令相同；dry-run 印出 `iptables -V` 偵測到的後端與現有鏈）：
  - 自建鏈 `FJU-CF-ORIGIN`（v4、v6 各一條），規則只套在「外網介面進來、目的埠 80／443、新連線」（`-i <預設路由介面> -p tcp -m multiport --dports 80,443 -m conntrack --ctstate NEW`）：來源在 Cloudflare 清單 → RETURN；其餘 → DROP。`DOCKER-USER` 的第一條 jump 到它。`--dports 80,443` 成立是因為 edge 的發布是 `80:80`、`443:443`（`DOCKER-USER` 看到的是 DNAT 之後的目的埠）；若日後改成不同埠對應，要改用 `-m conntrack --ctorigdstport`。容器之間、VM 自己對外（Let's Encrypt、GHCR、Doppler）都不經這條，不受影響；Let's Encrypt 的 HTTP-01 挑戰經 Cloudflare 代理進來，來源是 Cloudflare，照常放行。
  - 預設只印不做；`--execute` 可重跑（先清自建鏈再重建）；`--release` 拿掉 jump 與自建鏈；非 root 只印。
  - **重開機會掉**：`DOCKER-USER` 的規則不會自動持久化。`--execute` 同時寫一個 systemd oneshot `fju-cf-origin-lock.service`（`After=docker.service`、`WantedBy=multi-user.target`，`ExecStart` 就是本腳本 `--execute`）並 enable；`--release` 一併 disable 並刪單元。不裝 `iptables-persistent`（它會把 Docker 自己的規則一起存，重開機後與 Docker 重建的規則打架）。
  - IPv6：VM 若有公開 AAAA，Docker daemon 的 `ip6tables` 要開著才會把 v6 流量導進 `DOCKER-USER`；dry-run 印出 `docker info` 的 ip6tables 狀態與 VM 的全域 v6 位址，README 寫明「沒有 AAAA 就只驗 v4；有 AAAA 但 ip6tables 關著 → 先在 daemon.json 開或拿掉 AAAA，不能放著不管」。
  - Cloudflare 清單與 Caddy 共用同一份（同一個抓取日期）；更新清單＝改檔、重跑 `--execute`。這是 Roy 切橘雲**之後**才跑的步驟，寫在 README。不在 Caddy 做 IP 擋：Caddy 擋了之後 Let's Encrypt 的挑戰若有一天不經 Cloudflare 就會失敗，而且換清單要重載 Caddy。
- 驗證：`docker run --rm -v "$PWD/ops/Caddyfile.vm:/etc/caddy/Caddyfile:ro" caddy:2.10-alpine caddy validate --config /etc/caddy/Caddyfile`；`web/test/ops/ops-guards.test.ts` 的「中文語系 `${VAR}`」掃描自動涵蓋新腳本；補兩個用例：dry-run（不是 root、不帶 `--execute` → 只印偵測結果與完整 `iptables`／`ip6tables`／`systemctl` 指令序列，不呼叫真命令）；`--execute` 在 PATH 假命令下（`iptables`、`ip6tables`、`systemctl`，加一支回 `0` 的假 `id` 讓 root 判斷過）驗呼叫順序是「清鏈 → 建鏈 → 加規則 → jump → 寫單元 → enable」。root 判斷若改用 `EUID` 不能假造，就只驗 dry-run 輸出含完整序列（二擇一，PR 說明）。

### 4.3 app 端：不改

`x-real-ip` 優先的讀法不動；e2e 直接在請求上注入 `x-real-ip` 的作法（沒有 Caddy）照舊可用，既有限速測試不受影響。

### 4.4 Roy 的 Cloudflare 操作清單（寫進 `ops/README.md`「Cloudflare」一節，順序即步驟）

1. 先合 ⑤-04（Caddy 支援兩種模式）並部署到測試站、正式站。
2. DNS：測試站與正式站 A／AAAA 記錄打開代理（橘雲）。先測試站、確認後再正式站。
3. SSL/TLS：加密模式 **Full (strict)**（來源是 Let's Encrypt 憑證，strict 可過）。**關**「Always Use HTTPS」、「Automatic HTTPS Rewrites」、「Opportunistic Encryption」（最後一項可開可關，建議關）。HSTS 不在 Cloudflare 開（app 的 CSP／安全標頭由 app 管）。
4. Speed → Optimization：**關** Rocket Loader 與 Email Address Obfuscation（Free 方案只有這兩個會動 HTML；Mirage／Polish 是付費功能，Auto Minify 已下架）。理由：它們往 HTML 注入 inline script 或改寫標籤，直接撞 CSP（全站 `script-src` 沒有 `unsafe-inline`，規格限制）。Brotli 可開。
5. Caching：§3.2 的那一條 Cache Rule；Browser Cache TTL 設「Respect Existing Headers」。
6. Security → WAF：一條 Rate limiting rule（Free 方案 1 條）：路徑 `/api/auth/*` 或 `/login`，同一 IP 10 秒內超過 30 次 → 封鎖 10 秒。這是 app 限速之外的粗網，不取代 app 的規則。**Bot Fight Mode 關**：Free 方案不能用 WAF 規則放行，會擋掉驗收夜的 Playwright、教學錄影與 health-cron 的 curl；Browser Integrity Check 可開。
7. 切橘雲後，VM 上先跑 `sudo ops/cloudflare-origin-lock.sh`（只印）看規則與偵測結果，再 `--execute`。驗證（AC-26）：從 VM 以外直接對 VM 的 IPv4 打 `:443`、`:80` 被拒或逾時；VM 有 AAAA 時對 IPv6 位址同樣被拒（沒有 AAAA 就記「無 v6」）；經網域仍 200；`sudo iptables -S DOCKER-USER | awk '$1=="-A" && $2=="DOCKER-USER" {print; exit}'` 取得第一條規則，預期為 `-A DOCKER-USER -j FJU-CF-ORIGIN`（不用 `head -1`：`-S` 第一行是 `-N DOCKER-USER`）；重開機後重驗（同一指令、同一結果）；憑證須在來源限制**持續啟用**時成功續期（`docker logs fju-edge-caddy` 看到續期成功，當時第一條規則仍是上面那條）；解除限制（`--release`）後的續期不算 AC-26 通過。
8. 驗證：登入錯 5 次確認被鎖的是自己不是全站（AC-9）；`/api/health` 經 Cloudflare 仍 200 且 `cache-control: no-store`（health-cron 已經打網域，不用改）。
9. 上傳上限（**主腦已裁定 Q4，Roy 要在 Doppler 操作**）：Cloudflare Free 方案每個請求 body 上限 100 MB；app 的 `FILE_MAX_BYTES` 預設 100 MiB（104,857,600）略大，超過 Cloudflare 上限會先被 Cloudflare 回 413，看不到 app 的友善訊息。不改程式，改 Doppler：Doppler → 專案 `fju-im-capstone` → config `stg` → 鍵 `FILE_MAX_BYTES` → 值改成 `99614720`（95 MiB）→ Save；`prd` 同樣；然後兩站各重跑一次 `deploy.sh`（值在每次部署重新取，見《02 環境變數》「恢復」列）。切橘雲前做；上傳頁的上限文字由程式算，會自動顯示 95 MB。
10. 舊的 fju-status 的 Cloudflare Access 應用與 DNS 記錄一併刪（§6）。

## 12. 不做的事（附理由）

1. **不搬 Cloudflare Workers、不用 Cloudflare Tunnel**：Roy 定案 VM 不動；Tunnel 需要在 VM 裝 cloudflared 並改 Caddy 架構，收益只有「不用開 80／443」，在 `DOCKER-USER` 鏈限制來源已夠（ufw 擋不到 Docker 發布埠，見 §4.2）。
2. **不換 Cloudflare Origin CA 憑證**：Let's Encrypt HTTP-01 經代理可用（§4.2），少一份要人工更新的 15 年憑證。
3. **不做自製監測頁、不保留 Gatus**：Roy 只看 Cloudflare、GA4、Discord。
4. **不在 app 加 `s-maxage` 或下架時 purge Cloudflare**：5 分鐘的陳舊視窗與今日公開圖片一致；purge 需要 Cloudflare API token 進 app 的 secrets，多一個攻擊面（待問 Q3）。
5. **不開 Cloudflare「Always Use HTTPS」**：會讓 Let's Encrypt 續期經 443 走，Caddy 的 HTTP 挑戰在 80；轉址 Caddy 已做。
6. **不加 `charLength()` 的 lint 規則**：誤報多（§9）。
7. **不回改 41 個用 `86_400_000` 的 e2e**：風險高、收益低；新 helper 只給新 spec。
8. **不抽名單 fixture**：單一使用者。
9. **不做 `verify --e2e` 的 CI 環境注入**：已存在。
10. **不在 ⑤ 修封存漏擋的命令**：⑤-12 只補測試，漏擋開子票給該模組的擁有者（①③）；⑤-12 的 issue 等子票全部合併、`it.fails` 清空才關。
11. **不刪 `docs/plans/2026-10-12-status-console/**` 與 `2026-10-16-status/**`**：歷史紀錄，刪了既有 PR 的連結會失效。
12. **不改 `register/verify/page.tsx` 的導向**：已驗證者導去 `/register/apply` 是對的；要改的是 action 的回覆。
13. **⑤ 沒有 migration、不碰 `fingerprints.ts`、`budget.json`、`sql-expect.json`（⑤-15 除外）**。
14. **不做 Discord 通知抑制（連續失敗只報一次）**：GitHub Actions 無狀態，做抑制要再查 API；10 分鐘一則可在頻道靜音，恢復通知已夠。
