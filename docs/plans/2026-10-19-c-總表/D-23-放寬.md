## 0. 結論先講

- **問題**：嚴格規則下，`e2e/fingerprints.ts`（頁面指紋）、`scripts/perf/sql-expect.json`（查詢數期望）、`scripts/perf/budget.json`（打包預算）一次只能一張票改，總表為此加了一長串「排隊」前置，最長鏈約 **92 小時**（以今天已合的票重算；10/19 凌晨估的 96 小時還沒扣掉之後合進的票）。
- **做法**：新開一張前置票 **C INFRA-2（M，約 4 小時，沒有前置）**：三個檔**留在原位、內容不動**，當「基底」；旁邊各開一個資料夾放「每張票一個小檔」（overlay），讀取端在讀的時候把基底和小檔合併。之後的票只新增或修改**自己的小檔**，不同票就不會改到同一個檔。
- **合併規則的重點**：同一個鍵（同一條路由）被兩張票同時動、或沒宣告就蓋掉別人的值，一律**報錯**（e2e 載入失敗、`perf:bundle`／`perf:sql` exit 1），不會默默覆蓋。
- **效果**：拿掉 15 條只為這三個檔而加的前置（另把⑤-15 ← C3-12 一起拿掉，共 16 條）；原本經由這些排隊邊「順便」串住的另外兩組共檔要改成明寫（C3-12 ← C2-22、⑤-15 ← C1-06）。最長鏈從約 **92 小時**降到約 **61 小時**（少約 31 小時）。
- **要改的 issue**：**19 張**（另新開 INFRA-2 一張）。其中 14 張拿掉排隊前置並加 INFRA-2（⑤-15 另補明寫 C1-06），1 張（C3-12）補明寫 C2-22 並加 INFRA-2，4 張只加 INFRA-2。

- **基底不搬、不改內容**：這樣在審的 C2-16 #727（唯一改到 `budget.json` 的在審票）不論在 INFRA-2 之前或之後合，都不會撞（見 §6）。
- **檔名規則**：`^(C[1-4]-\d{2}|C5-\d{2}|INFRA-\d+)([a-z]|-fix\d+)?\.json$`；⑤的票用 ASCII `C5-NN`（例：⑤-15 → `C5-15.json`），避免檔名用全形符號。**子票**（例如⑤-12 漏擋命令開的子票、C1-18 的修補）＝原票號加一個小寫字母（`C5-12a.json`、`C1-18a.json`）；**修補票**＝原票號加 `-fix<n>`（`C2-22-fix1.json`）。開這類票時照此命名，規則就不會擋。檔內 `ticket` 欄必須等於檔名主幹。資料夾裡只允許符合規則的 `.json` 與一份 `README.md`；其他檔名（例如打錯字）直接報錯，避免小檔被靜默忽略。
- **小檔一律 JSON**（三種都一樣），讓同一支合併程式能被 e2e（TypeScript）與 perf 腳本（Node `.mjs`）共用。

### 1.3 小檔格式與合併規則

```json
{
  "ticket": "C1-13",
  "set": { "/dashboard/admin/grading/teachers": <值> },
  "override": { "/dashboard/admin/grading": { "from": "base", "value": <值> } },
  "delete": [{ "key": "/dashboard/admin/signoff", "from": "C1-11" }]
}
```

- `<值>`：指紋是非空字串；`budget` 是 `{ baseline, limit }`（兩個數字），**`limit` 必須等於 `limitFor(baseline)`**——沿用 Q106 與 `scripts/perf/bundle.mjs:30-33` 的算法（`ceil(baseline×1.1)`，`baseline ≤ 250` 時封頂 250，`baseline > 250` 時不封頂）；`sql-expect` 是 `{ as, baseline, max, identity, noDuplicate? }`。格式不對直接報錯。
  - 基底目前有 5 列不符合 `limitFor`（C2-01 加的 `/dashboard/admin/accounts/{disabled,pending,roster}`、`/dashboard/admin/grading/teachers`、`/dashboard/admin/groups/unassigned`：baseline 223.5、limit 寫死 250，`limitFor` 算出 246）。**基底不驗**；哪張票的小檔要 `override` 這 5 列，就照 `limitFor` 填。
- **`set`**：新增一個鍵。這個鍵不能已經在基底，也不能被別的小檔 `set` 過。
  - **把被刪掉的鍵加回來**：寫成 `"set": { "<鍵>": { "from": "<刪它的票>", "value": <值> } }`；只有當這個鍵目前的狀態是「被那張票 `delete`」時才允許，其他情況帶 `from` 的 `set` 一律報錯。
  - **兩張平行票都 `set` 同一個新鍵**：先合的那張成立；後合的那張 CI 會紅（`set` 撞 `set`），rebase 後把自己的那一項改成 `"override": { "<鍵>": { "from": "<先合的票>", "value": … } }`。
- **`override`**：改一個已存在的鍵，**必須寫 `from`**：`"base"`＝改基底的值；`"<票號>"`＝改那張票的小檔（已合進）設定的值。
- **`delete`**：刪一個已存在的鍵，同樣**必須寫 `from`**。
- **`$` 開頭的鍵**（`budget.json` 的 `$comment`、`$shared`、`$rules`；`sql-expect.json` 的 `$comment`）：
  - `$shared`：**只准 `override`**（不准 `set`、`delete`），值是 `{ baseline, limit }`，而且 `limit` 必須等於基底的 `$shared.limit`（目前 230，`SHARED_LIMIT_KB`）——也就是小檔只能改 `$shared.baseline`（C4-11 會用到），要改上限照舊走基底與 Review。
  - `$comment`、`$rules`：小檔**一律不准動**（任何動作都報錯）；`$rules` 的形狀跟路由列不同，驗證時直接跳過它、原樣保留基底值。要改它們就照舊改基底（或在 `overlay fold` 時一起改）。
  - 指紋沒有 `$` 鍵。
- 每個鍵的「目前主人」：基底的鍵主人是 `base`；被某張票 `set`／`override` 後，主人就變成那張票。`override`／`delete` 的 `from` 必須等於目前主人。
- **合併順序與確定性**：先讀基底，再依「`from` 鏈」逐鍵套用：同一個鍵上的動作必須排成一條鏈（`base` → A → B…）。檔名順序不影響結果。
- **一律報錯、不默默覆蓋**（錯誤訊息都寫出：哪個資料夾、哪兩個小檔、哪個鍵、哪一種衝突）：
  1. `set` 的鍵已在基底，或兩個小檔都 `set` 同一個鍵；
  2. `override`／`delete` 的鍵不存在，或 `from` 不是目前主人；
  3. **分叉**：兩個小檔對同一個鍵寫同一個 `from`（例：兩張票都從 `base` 改 `/dashboard/admin/grading`）；
  4. 同一個小檔裡同一個鍵出現兩次；未知欄位；`ticket` 與檔名不符；檔名不合規則；JSON 解析失敗；
  5. 刪掉的鍵之後又被別的小檔 `override`（等同不存在；要加回來用帶 `from` 的 `set`）；
  6. `budget` 的 `limit` 不等於 `limitFor(baseline)`、`$shared.limit` 跟基底不同、小檔動到 `$comment`／`$rules`。
- **報錯怎麼呈現**：`perf:bundle`、`perf:sql` 直接 exit 1 並印出訊息；e2e 是在 `fingerprints.ts` 被 import 時丟錯，所有用到它的 spec 都載入失敗（大聲失敗）；另有 `pnpm -C web overlay check` 一次檢查三個資料夾，單元測試也會跑真實資料夾（所以 `pnpm -C web verify` 就會擋）。
- **資料夾怎麼找**：基底 `X.json` → 小檔資料夾 `X.d/`（同層）。`bundle.mjs --budget <路徑>`、`sql.mjs --expect <路徑>` 給別的檔時，照同一規則找它旁邊的 `.d/`，不存在就當沒有小檔。

"""D-23 放寬後的前置檢查：除了三個共用檔（fp／sqlx／budget），任兩張還沒合的票只要可改檔案有交集，
