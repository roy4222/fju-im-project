## 3. B 階段做法

### 3.1 寄信：`Mailer` port、Brevo 轉接器、`mail_outbox`

**為什麼要一張表**：三種信（驗證碼、重設連結、審核結果）都要能在 e2e 與助教驗收時「看得到寄了什麼」，又不能在正式站留下驗證碼與重設 token。所以寄信一律先寫一列 `mail_outbox`；**正式寄出的列 `subject`、`body_text`、`error` 都不得含 OTP 或重設 token**（OTP 主旨本來就不含碼，§3.9；`body_text` 寫 `null`；`error` 只存 Brevo 的 HTTP 狀態碼與錯誤碼，不存回應全文）。只有**明確啟用擷取模式**的隔離測試環境把內文存進去。

- `web/src/application/mail/`（新模組）
  - `ports.ts`：`Mailer { send(message: MailMessage): Promise<Result<MailReceipt>> }`；`MailMessage = { to: string; template: MailTemplate; subject: string; text: string; html?: string }`；`MailTemplate = 'email_otp' | 'password_reset' | 'registration_result'`；`MailReceipt = { outboxId: string; status: 'sent' | 'captured' }`；失敗回 `err('MAIL_FAILED' | 'MAIL_NOT_CONFIGURED')`。
  - `templates.ts`：純函式產生三種信的 `subject`／`text`（內容 §3.9）。單元測試斷言 `email_otp` 的 `subject` 不含任何 6 位數字、`password_reset` 的 `subject` 不含 `token`。
  - `index.ts` 入口匯出。
- `web/src/infrastructure/mail/brevo-mailer.ts`（正式轉接器）：讀 `BREVO_API_KEY`、`MAIL_FROM`（例 `專題管理平台 <noreply@roy422.dev>`）、`MAIL_REPLY_TO`（選配）。先 insert `mail_outbox`（`status='queued'`，`body_text=null`）→ `POST https://api.brevo.com/v3/smtp/email`（用 `fetch`，逾時 10 秒）→ 成功 `status='sent'`、記 `provider_message_id`；失敗 `status='failed'`、`error` 只記 `brevo_<HTTP 狀態>_<code>` 或 `timeout`，回 `err('MAIL_FAILED')`。**缺 `BREVO_API_KEY` 或 `MAIL_FROM` → insert `status='failed'`、`error='not_configured'`，回 `err('MAIL_NOT_CONFIGURED')`，不降級為擷取。** 金鑰、收件內文不進 log 與 `error`（比照 #418 Review 的遮金鑰原則）。
- `web/src/infrastructure/mail/capture-mailer.ts`（擷取轉接器）：insert `status='captured'`、`body_text` 存全文，回 ok；**不打外部**。
- `web/src/composition/mail.ts`：選轉接器的唯一地方。`MAIL_CAPTURE === '1'` → 擷取；否則一律 Brevo。擷取模式**只限隔離測試環境**：`MAIL_CAPTURE=1` 只寫在 `.github/workflows/ci.yml` 的 `e2e-smoke` job `env`（:166 起，該 job 的 `BETTER_AUTH_URL` 是 `http://127.0.0.1:3000`）、本機 `.env.example` 註解，以及 **integration 測試由一個 setup 檔統一開**：`web/vitest.config.ts` 的 `integration` project 加 `setupFiles: ['./test/mail-capture-setup.ts']`，新檔只做 `process.env.MAIL_CAPTURE ??= '1'`（c0f32bd 沒有 `setupFiles`；會啟動 `auth-instance` 的 14 個 integration 測試檔都 `vi.stubEnv('BETTER_AUTH_URL', 'http://127.0.0.1:3000')`，過得了主機守門）——否則 VB-2 開了 `sendVerificationOnSignUp` 之後，這些測試裡每一次 HTTP sign-up 都會因 `MAIL_NOT_CONFIGURED` 失敗；**Doppler stg／prd 不得設**；`composition/mail.ts` 在 `MAIL_CAPTURE=1` 但 `BETTER_AUTH_URL` 的主機不是 `localhost`／`127.0.0.1` 時拒絕擷取、改走 Brevo（缺金鑰就照上面回 `MAIL_NOT_CONFIGURED`）並 log 一次警告。單元測試覆蓋三種組合（無旗標→Brevo、旗標＋127.0.0.1→擷取、旗標＋`https://*.roy422.dev`→Brevo）。
- **所有呼叫者都要處理失敗的 Result**（不 `await mailer.send(...)` 就丟掉回傳值）：OTP 回呼（§3.2）與重設回呼（§3.4）收到 `err` 時丟 `APIError('INTERNAL_SERVER_ERROR', { code: 'MAIL_FAILED' })`，畫面轉成「驗證信寄不出去，請稍後再試」；忘記密碼對外仍一律進「已寄出」（不洩漏帳號存在），失敗只留 `mail_outbox.status='failed'`。審核結果信失敗不回滾、不回錯（下段）。

### 3.2 Email 驗證（Better Auth `email-otp`）與未驗證帳號的限制

- `web/src/infrastructure/auth/auth-instance.ts`
  - `plugins: [emailOTP({ otpLength: 6, expiresIn: 600, allowedAttempts: 5, storeOTP: 'hashed', sendVerificationOnSignUp: true, overrideDefaultEmailVerification: false, sendVerificationOTP: async ({ email, otp, type }) => { if (type !== 'email-verification') throw new APIError('FORBIDDEN'); const r = await mailer.send(templates.emailOtp(email, otp)); if (!r.ok) throw new APIError('INTERNAL_SERVER_ERROR', { code: 'MAIL_FAILED' }) } })]`。只用 `email-verification` 型別；`sign-in`、`forget-password` 型別的端點在 route-matrix 擋掉。`storeOTP: 'hashed'`（1.7.5 `plugins/email-otp/otp-token.mjs:11`）讓 `verifications` 表也不存明文碼；套件預設是 `'plain'`（`index.mjs:16`），**必須明寫**。
  - **首次寄碼在伺服器內觸發**：`sendVerificationOnSignUp: true` 讓套件在 `/sign-up/*` 成功後的 `hooks.after`（1.7.5 `plugins/email-otp/index.mjs:50-70`）直接產碼、存碼、呼叫 `sendVerificationOTP`——**不再由前端或 Server Action 用同一個 Turnstile token 再打一次寄碼端點**（Turnstile token 只能驗一次，[Cloudflare siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)）。這條路徑不經公開寄碼端點，所以由 sign-up 自己的 Turnstile 與 `register` 桶保護，另外在 `hooks.before` 的 sign-up 分支一併扣 `otpSend` 的 email 桶一次（同一個 Email 重送註冊不能繞過寄碼上限）。
  - `emailAndPassword` 加 `sendResetPassword: async ({ user, url }) => { const r = await mailer.send(templates.passwordReset(user.email, url)); if (!r.ok) log（不含 url） }`（失敗不往外拋：對外一律「已寄出」，§3.1）、`resetPasswordTokenExpiresIn: 1800`（30 分鐘，原型文案「連結 30 分鐘內有效」）、**`revokeSessionsOnPasswordReset: true`**（1.7.5 `api/routes/password.mjs:171`；不設就不撤 session，AC-VI-60 需要）。`url` 由 Better Auth 依 `redirectTo` 組成 `${BETTER_AUTH_URL}/reset-password?token=…`（呼叫 `request-password-reset` 時帶 `redirectTo: '/reset-password'`）。
  - `requireEmailVerification` **維持不設**（§1 第 9 條）。
  - **限速**（Review 6；`web/src/shared/rate-limit.ts:100-134` 的 `RATE_LIMITS` 加三桶，由 `hooks.before` 執行，**HTTP 與 Server Action→`auth.api` 兩條路徑都經過 `hooks.before`**，所以共用同一組桶；`wrapper.ts:210` 已依賴這件事）：
    - `otpSend`：5 次／10 分鐘／email＋20 次／小時／IP；套用在 `/email-otp/send-verification-otp`（HTTP 與內部入口）與 sign-up 觸發的首次寄碼。
    - `otpVerify`：10 次／10 分鐘／email＋60 次／小時／IP；套用在 `/email-otp/verify-email` **與** `/email-otp/check-verification-otp`（兩條共用一桶，check 不能拿來繞過 verify 的上限）。單一驗證碼仍是 `allowedAttempts: 5`——連錯 5 次該碼作廢（AC-VI-47），與桶無關。
    - `passwordReset`：5 次／小時／email＋20 次／小時／IP；套用在 `/request-password-reset`。
    - **120 秒重寄冷卻由伺服器執行**：`otpSend` 另有 `otpResendCooldown`（1 次／120 秒／email），前端倒數只是顯示；冷卻內打端點回 429 `RATE_LIMITED`。
    - **套件自己的限速明確覆寫**：email-otp 外掛對 `/email-otp/send-verification-otp`、`/check-verification-otp`、`/verify-email` 等預設 3 次／60 秒（1.7.5 `plugins/email-otp/index.mjs:75-120`，只在 HTTP 的 `onRequestRateLimit` 跑、鍵只有 IP＋路徑，跨帳號共用一桶）。比照 `auth-instance.ts:151` 既有作法，在 `rateLimit.customRules` 把這三條設成 `false`，只留我們自己的桶；`route-table.integration.test.ts`（套件限速設定守門）的路徑清單加這三條（`toBe(false)`）。
  - **續辦未完成的註冊**（Review 5；**不刪 `users`／`accounts`**，§1 第 11 條）：sign-up 遇到同 Email 已存在時，`hooks.before` 照舊回 `EMAIL_UNAVAILABLE`（不覆蓋、不刪）。改由第 1 步的 Server Action 在收到 `EMAIL_UNAVAILABLE` 時判斷能否**續辦**：

- **三個寄信表單、三條受保護的公開路徑**：`/sign-up/email`（Email 註冊第 1 步）、`/request-password-reset`（忘記密碼）、`/email-otp/send-verification-otp`（第 2 步重寄驗證碼）。**首次驗證碼由 sign-up 成功後在伺服器內寄**（§3.2 `sendVerificationOnSignUp`），不再用同一個 token 呼叫寄碼端點；**重寄每次取得新 token**（widget 在送出後 `turnstile.reset()`）；`/account` 的「驗證 Email」走 fresh session 的內部寄碼入口，**不掛 widget**（§3.7）。
