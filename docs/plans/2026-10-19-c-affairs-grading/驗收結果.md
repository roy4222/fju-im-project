## 結論（白話）

規格①的 18 張票（C1-01～C1-17）＋C2-22 都合進 `stage-c` 之後，在 `stage-c` = `5b5e0483` 上把整套測試、打包大小、查詢數、端到端流程（AC-37）全部跑過一次：

- **AC-1～AC-36 全部有測試在綠燈下守著**；AC-37 端到端用 Playwright 在示範資料上照十個步驟手跑一遍，**十步全過**、全程沒有 CSP 違規。

- 打包大小 84 條路由都在預算內；查詢數四個角色都在期望內。
- 沒有發現要開修補票的破洞；有幾個小觀察寫在最後「觀察」一節，不擋驗收。

## 觀察（不擋驗收，沒有開修補票）

1. **同意書通知的字樣比規格多「組別＋第 N 版」**：規格 AC-21／AC-23 寫「有一份同意書輪到你同意」「同意書內容已更新，請重新閱讀並同意」，實際是「G07「期中結果確認」第 1 版輪到你閱讀並同意」「G07「期中結果確認」第 2 版內容已更新，請重新閱讀並同意」。跟既有簽核通知同一種寫法，意思一樣；但 AC-22 要求頁面不顯示版本號，通知裡卻有「第 N 版」。要不要拿掉版本號，請主腦決定。
2. **`/rules` 有兩個叫「評分方式」的區塊**：示範資料第 8 章的章名是「八、評分方式」，C1-14 新加的評分比例區塊標題也是「評分方式」。用 `getByRole('region', { name: '評分方式' })` 會同時找到兩個（螢幕報讀也分不太清）。`rules-weights.spec.ts:94` 也是這樣找，它自己造的規則沒有這個章名所以沒撞到；在示範資料上會撞。可以考慮把示範第 8 章改名或把區塊標題改成「評分方式與比例」。
3. **五欄的查詢數指令有一條跑不起來**：訪客 `/files` 從 T1 起就轉登入頁，`perf:sql` 對 307 一律 exit 1。本次改成學生身分量 `/files`。之後別的票照抄這條指令會撞到。
4. **本機跑全套 e2e 要帶 `IDENTITY_CACHE_TTL_SECONDS=0`**：`web/AGENTS.md` 的範例有帶，但五欄的「`pnpm -C web verify --integration src test --e2e e2e`」沒寫；不帶會有 2 條身分快取相關的測試紅。
5. **AC-35 的「`LATEST='0021…'`、表數 71」已經被③的 0022～0024 取代**，驗收時以 migrations 整合測試的現值為準。
