### 1.2 同意書連到作業（schema `signoff.ts`）

- **新欄** `signoff_packages.item_id uuid null references managed_items(id)`；索引 `(item_id)`。一個同意書作業（`consent_mode='form'`）對 N 個 package（每個對象組一包，`purpose` 沿用）。
- **唯一鍵改法**：現有 `signoff_packages_group_purpose_unique (group_id, purpose)` 會讓同一組第二份同用途同意書（例如改版重發、或下一學期再發一次「期中結果確認」）撞鍵。0022 `drop constraint signoff_packages_group_purpose_unique`，改成兩條 partial unique index：`signoff_packages_group_item_unique on (group_id, item_id) where item_id is not null`、`signoff_packages_legacy_group_purpose_unique on (group_id, purpose) where item_id is null`。舊 API `createVersion(groupId, purpose)`（整合測試用）繼續只操作 `item_id is null` 的包、行為不變；新路徑一律以 `(group_id, item_id)` 找包。`SignoffQuery.studentView/teacherView` 加 `byItem(groupId, itemId)` 版本，舊簽名保留給測試。
- 不改 `signoff_package_versions`、`approvals`、`signoff_version_status`、`signoff_exports`；不動 trigger、不動 `content_checksum` CHECK。
- **草稿不建包**：`create`／`saveDraft` 只存作業本身（含 `consent_mode`、`consent_purpose`、正文、附件）；包只在 `publish` 建。
- **發布同意書作業時**（`ItemCommand.publish`，`collectsResponses` 且 `consent_mode='form'`）：在同一交易裡呼叫新的 `ConsentPublishHook.onPublished(tx, item)`（§3.1 介面）：對每個對象組 → 若該組有主指導且有有效組員 → 建包（`item_id`＝此作業）＋第 1 版（內容＝item 目前版本的 `body_html`，`purpose`＝`managed_items.consent_purpose`，參與者快照照舊，發既有 `signoff.version_created` 給組員）。**附件＝item 附件**，用明確的 item 附件來源綁版本：`#createVersionInTx` 的 `attachments: { source: 'item_attachment', itemId, fileIds }`，以既有 `FileStorage.attach(tx, fileId, {refType:'signoff_version', refId}, { purpose: 'attachment', heldBy: { refType: 'item_attachment', refId: itemId } })` 證明「這個檔此刻是這份作業的附件」（item 來源綁檔須傳 `{purpose:'attachment', heldBy:{refType:'item_attachment',refId:itemId}}`），**不走**舊路徑「必須是本組正式送出的繳交檔」那條檢查（那條只給 `item_id is null` 的舊 API）。reset／reopen 重綁須依檔案實際用途驗證，保留舊 submission 來源；attachment 下載政策另接受經既有簽核版本讀權驗證的 `signoff_version` 引用，不得放寬其他附件（§3.3）。**最終文件授權**（`consent_purpose='final_document'`）：逐組解析該組成果展示條目的草稿（既有 `createVersion` 的 `showcaseEntryId` 路徑，`FOR SHARE`）並凍結 `authorization_scope`；**任一對象組沒有草稿 → 整筆發布拒絕**（`VALIDATION_FAILED`「這些組還沒有成果展示草稿：G03、G06」，交易回滾、不建任何包、作業仍是草稿）；`result_confirmation` 不帶範圍、不查草稿。沒有主指導或沒組員的組 → 不建包，回傳 `skipped: [{groupId, reason:'no_advisor'|'no_members'}]` 讓繳交狀況頁顯示「尚未建立：沒有指導老師」與「建立」鈕（指派老師後由系辦按一下補建 `ConsentPublishHook.createForGroup`；不自動）。**`consent_mode='form'` 的作業不發 `item.published`**（避免同一批人收到「新作業」＋「輪到你同意」兩則）；`upload` 模式照常發 `item.published`。
- **發布更新且內容或附件有變**（`updatePublished` 有 `content_change`）：呼叫 `onContentChanged(tx, item)` → 每個目前版本在收集中／等老師／已完成／**退回修正中（`revision`）**的 package 建新版（退回後系辦改內容本來就是解法，不能卡在 revision 等手動 reset），`supersede_cause='content_change'`，舊版 `superseded`；**舊同意留歷史、不計入新版、每個參與者（含已同意的學生與已同意的主指導）都收到通知**。既有 `signoff.superseded` 事件現行**只通知系辦**（Roy 2026-09-25 定案），不能改它的收件規則；因此新增事件 **`signoff.content_changed`**（kind `signoff`，consumers `['notifications']`，標題「同意書內容已更新，請重新閱讀並同意」，收件人＝被取代那一版參與者快照裡的全部學生＋主指導），由 hook 在建新版時發。**一版只發一種建版通知**：`#createVersionInTx` 帶 `notify: 'version_created' | 'content_changed'`，內容改版的新版只發 `signoff.content_changed`、**不再發** `signoff.version_created`；`signoff.superseded` 仍照舊發給系辦（系辦自己改的就 recipients 空）。「附件有變」＝附件集合或任一檔案版本（checksum）變，新版以 item 附件來源重綁新集合。這就是 #161 的答案（§6.4 有畫面）。只改對象、截止、標題不觸發新版。
- `response_rosters` 對同意書作業照常建立（**整組收件**，一列一組），用來算「繳交狀況」的分母與催繳名單；該組「已交」＝package 目前版本 `complete`，「未繳」＝`collecting`／`teacher_pending`／`revision`，「尚未建立」＝沒有包（§6.3）。
- `signoff_packages.item_id is null` 的舊資料：系辦在作業分頁底部看到一塊「舊同意書（未連結作業）」唯讀列，連到原詳情頁（路由轉址歸②）。測試站只有示範資料，凍結期用 `seed-demo --remove` 後重 seed（§1.7），正式站還沒開，所以不寫 SQL 回填。

### 1.3 評分項目 ↔ 作業連結（schema `grading.ts`）

- **新表** `grading_stage_settings (cohort_id uuid not null references cohorts(id), stage_key text not null, item_id uuid null references managed_items(id), description text null check (description is null or char_length(description) between 1 and 500), panel_key text null check (panel_key is null or char_length(panel_key) between 1 and 40), updated_by_user_id uuid not null references users(id), updated_at timestamptz not null default now(), primary key (cohort_id, stage_key), check (item_id is not null or description is not null or panel_key is not null))`。`web/src/infrastructure/db/permissions/matrix.json` 新列 slice **`C1`**：select／insert／update(`item_id`,`description`,`panel_key`,`updated_by_user_id`,`updated_at`)／delete true（三欄都清空＝刪列）；`roles.integration.test.ts` 的 `SAMPLES` 補一列。
- 為什麼不放進 `stages` jsonb：`stages` 寫了不可變、第一位老師填分後整版鎖定；對應作業與說明都**不影響分數**（連結只決定老師批改時看哪份繳交，說明只是給老師看的文字），系辦在學期中隨時要能改（例如期中之後才建「系統驗收文件」作業再掛上去、或補一句評分說明），放 jsonb 會逼著建新版＋套用重算。側表＝改了不建版、不鎖、不重算。**`description` 也放側表**，不進 jsonb，`normalizeSchemeStages` 不改。
- **stage_key 生命週期**：`SchemeEditor` 建新版時沿用既有 stage 的 `key`（`grading-forms.tsx:53,65`），只有新加的才補 `s{n}`（`scheme.ts:235`），所以 key 跨版本穩定。讀取規則：所有讀側表的查詢（`teacherBenchPage`、`GradingRulesPanel`、`PublicGradingQuery`）都 **join 目前已發布版本的 stages**，key 不在裡面的列不讀；`publish` 新版同交易內 `delete from grading_stage_settings where cohort_id=$1 and stage_key not in (新版 keys)`。沒有已發布版本時側表不可寫（`VALIDATION_FAILED`「請先發布評分規則」）。
- 沒有對應作業的評分項目（例如「態度」）＝`item_id null`＋`description`；老師只看到標題＋說明＋直接填分（細項只有一個「總分」是方案結構，在評分規則勾「直接填總分」時 UI 代填 `items=[{name:'總分',type:'number',max:100,weight:100}]`）。

- **評審組（T2-3「驗收與總評由同 3 位老師各自評」）**：同一屆 `panel_key` 相同（非 null）的評分項目共用同一組評審；靠這欄、不靠項目名稱、不改四張評分表（§0.3）。約定＝「對每一組，panel 內每個項目的有效指派老師集合與 `required_count` 完全相同」，由 application **原子**維護：`assign`／`removeAssignment`／`setRequirement` 收到 panel 內任一 `stageKey`，就在**同一交易**對 panel 內全部項目做同一件事（同一位老師、同一 `choice`、同一 `required_count`、同一 `reason`），鎖序照既有（`groups FOR SHARE` → `stage_requirements`／`evaluator_assignments FOR UPDATE`，依 `stage_key` 排序），任一項目失敗整筆回滾。把已有指派的項目**加進** panel（`setStageSetting` 給 `panelKey`）時先檢查：有任何一組在這些項目間老師集合或 `required_count` 不一致 → `VALIDATION_FAILED` 列出組別（「G03、G07 的『系統驗收』與『專題發表』評審不同，請先在評分老師分頁對齊」），**不自動補指派、不結束任何指派**；拿掉 panel（`panelKey=null`）只解除約定，不動指派。已有分數的指派不因 panel 變動被結束（結束只走 `removeAssignment` 的既有三選一，對 panel 內每個項目各自套用既有規則；分數仍各項目一份、平均各算）。發布新版清側表列時 `panel_key` 跟著清。示範資料**不設**評審組（示範只有「系統驗收」有指派）。

## 7. 評分（T2、T2-模型、T2-1、T2-2、T2-3、X5、A27、X7）

### 7.1 模型（不改表，只加連結與用詞）

- 一組有幾個評分項目（stage）就有幾份成績（每個 `evaluator_assignments` 一份 `evaluations`）。✅ 既有。
- 每個評分項目可對應一份作業（`grading_stage_settings.item_id`）或不對應（只有標題＋說明 `description`＋直接填分：細項只有一個「總分」，滿分 100、權重 100；系辦在評分規則勾「直接填總分」時 UI 自動產生）。對應與說明改了都不建新版（§1.3）。T2-2。

- 細項與配分（T2-1）：評分規則頁可自己加減評分項目、細項、滿分、權重；規格不列實際項目。方案版本規則不變（寫了不可變、第一位老師填分後鎖定、要改結構建新版＋套用）。

### 11.3 前台直接編輯（A8）：②集中定義 registry，①只提供各 kind 的表單模組

②的 Review 裁定（2026-10-19）：前台直接編輯的表單 **registry 由②集中定義與登錄**；①只照②的契約提供模組。②的契約**已定版**在 `origin/claude/spec-c-admin-structure` 的《設計方案.md》§6.3.1（核對時為 `36230b82`），**以②為準**；本節照那一版寫。②§6.3.1 的要點（①照做）：

- 型別（②的 `_ui/front-edit/forms.ts` 定義、①只 import）：`FeKind`、`FeFields = Record<string, string | number | boolean | null>`、`FeFormProps { mode: 'edit' | 'add'; kind: FeKind; id: string | null; revision: number | null; cohortId: string | null; fields: FeFields; onDone(result?: { id: string; status?: 'draft' | 'published' | 'saved' }): void; onCancel(): void }`、`FeFormModule { default: ComponentType<FeFormProps>; remove?(input: { id: string; revision: number | null; requestId: string }): Promise<{ ok: true } | { ok: false; message: string }> }`。`FeFields` 只容許純值，①**僅供開窗提示，不作完整編輯初值**（附件、繳交欄位、選定組別陣列裝不進去，見下方 adapter 第 1、2 步）。

- 責任切分：**表單**自己呼叫自己的 server action（`requestId` 冪等）、自己顯示欄位錯誤與 `STALE`／`CONFLICT`（revision 不符）訊息、自己管送出中的按鈕狀態；**框架**（②）負責開關窗、刪除確認、`onDone` 後的 toast＋`router.refresh()`＋關窗、`remove` 成功後的 toast＋refresh、找不到 kind 時的提示。表單**不得** `router.push`、不得自己 `router.refresh()`、不得自己發 toast。`onDone` 的回傳值框架只拿來組 toast 與記 log，不依賴它。
- `remove`：有才能刪；框架先跳確認再呼叫；回 `ok:false` 時框架把 `message` 顯示在確認框、不關窗。不能刪的原因（`deleteCheck` 訊息）由②的標記骨架放 `data-fe-del-reason`，資料由①的頁面查詢提供。

`ItemForm` 系列 adapter 的做法（五個 kind 共用 `admin/affairs/front-edit/item-adapter.tsx`，各 kind 檔只 `export default` 綁 `placement`、`export const remove`）：

2. `mode:'edit'` → 以 `itemId=id` 呼叫 action，**必須**依 itemId 載入完整 `detail`，再用 `toInitial(detail)`（§2.7 同一函式）當 `initial`，`revision` 同取 `detail.revision`；載入成功前禁止送出（送出鈕 disabled、表單顯示載入中）。`FeFields` 僅供開窗提示（例如先顯示標題），不作完整編輯初值。`mode:'add'` → `defaultItemDraft(placement, cohortId)`。含附件及指定組別的項目從前台只改標題 → 其他欄位不被清掉（AC-6a）。
3. 固定 `layout='dialog'`；`CONFLICT`／欄位錯誤由 `ItemForm` 自己顯示（既有訊息「別人剛改過，請重新開啟」）。
4. `ItemForm` 的 `onDone({itemId,status})` 轉成 `onDone({ id: itemId, status })`（`status` 對應 `'draft' | 'published'`）。
5. `remove = ({ id, revision, requestId }) => deleteItemAction(...)`，把既有 `Result` 轉成 `{ ok: true } | { ok: false, message }`（不能刪的訊息照 `deleteCheck`）。

## 12. 風險

1. **②的殼與①的內容要同時到位才看得到畫面**。緩解：§11.2 掛載行視為例外檔；波次上②的殼票在第 2 波前合進 `stage-c`。
2. **同意書 hook 在 items 交易裡呼叫 signoff**：兩個模組同交易、鎖順序 `cohorts FOR SHARE → groups FOR SHARE → managed_items FOR UPDATE → signoff_packages`（契約 01 §6 順序延伸）；整合測試加並發用例（發布同意書作業 vs 同時加組員）。
3. **編輯器路由預算**只剩 8.3 KB；表單產生器與拖曳全部手寫；`AttachmentDrop`、`FieldBuilder` 進同一個 chunk；CI `perf:bundle` 擋。
4. **老師交作業的授權擴大**：`authorizeReceiver` 嚴格綁名單（不是所有老師），整合測試加「不在名單的老師被拒」。
5. **催繳寄信量**：一次最多全屆（~60 人）；Brevo 10 s timeout、fire-and-forget；不做批次佇列（正式站規模小）。
6. **示範資料重 seed**：測試站凍結期執行；`--remove` 會拒絕有真實資料引用的情況（既有保護）。
7. **評審組原子展開**：一次 `assign` 可能寫多筆 `evaluator_assignments`，鎖序固定依 `stage_key` 排序；整合測試加「兩個系辦同時對同一組的兩個項目指派」用例。
8. **每票獨立綠**：前票不得破壞呼叫端（`unassignedSlots` 字串版保留、`QuickCreateDialog` 留相容包裝到 C1-07）；每票合併前 `pnpm -C web verify` 自己要過。
