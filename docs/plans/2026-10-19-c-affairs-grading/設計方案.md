### 1.2 同意書連到作業（schema `signoff.ts`）

- **新欄** `signoff_packages.item_id uuid null references managed_items(id)`；索引 `(item_id)`。一個同意書作業（`consent_mode='form'`）對 N 個 package（每個對象組一包，`purpose` 沿用）。
- **唯一鍵改法**：現有 `signoff_packages_group_purpose_unique (group_id, purpose)` 會讓同一組第二份同用途同意書（例如改版重發、或下一學期再發一次「期中結果確認」）撞鍵。0020 `drop constraint signoff_packages_group_purpose_unique`，改成兩條 partial unique index：`signoff_packages_group_item_unique on (group_id, item_id) where item_id is not null`、`signoff_packages_legacy_group_purpose_unique on (group_id, purpose) where item_id is null`。舊 API `createVersion(groupId, purpose)`（整合測試用）繼續只操作 `item_id is null` 的包、行為不變；新路徑一律以 `(group_id, item_id)` 找包。`SignoffQuery.studentView/teacherView` 加 `byItem(groupId, itemId)` 版本，舊簽名保留給測試。
- 不改 `signoff_package_versions`、`approvals`、`signoff_version_status`、`signoff_exports`；不動 trigger、不動 `content_checksum` CHECK。
- **發布同意書作業時**（`ItemCommand.publish`，`collectsResponses` 且 `consent_mode='form'`）：在同一交易裡呼叫新的 `ConsentPublishHook.onPublished(tx, item)`（§3.1 介面）：對每個對象組 → 若該組有主指導且有有效組員 → 建包（`item_id`＝此作業）＋第 1 版（內容＝item 目前版本的 `body_html`，附件＝item 附件，`purpose`＝item 進階設定的用途，參與者快照照舊，發既有 `signoff.version_created` 給組員）；沒有主指導或沒組員的組 → 不建包，回傳 `skipped: [{groupId, reason:'no_advisor'|'no_members'}]` 讓繳交狀況頁顯示「尚未建立：沒有指導老師」與「建立」鈕（指派老師後由系辦按一下補建 `ConsentPublishHook.createForGroup`；不自動）。**`consent_mode='form'` 的作業不發 `item.published`**（避免同一批人收到「新作業」＋「輪到你同意」兩則）；`upload` 模式照常發 `item.published`。
- **發布更新且內容或附件有變**（`updatePublished` 有 `content_change`）：呼叫 `onContentChanged(tx, item)` → 每個目前版本在收集中／等老師／已完成／**退回修正中（`revision`）**的 package 建新版（退回後系辦改內容本來就是解法，不能卡在 revision 等手動 reset），`supersede_cause='content_change'`，舊版 `superseded`；**舊同意留歷史、不計入新版、每個參與者（含已同意的學生與已同意的主指導）都收到通知**。既有 `signoff.superseded` 事件現行**只通知系辦**（Roy 2026-09-25 定案），不能改它的收件規則；因此新增事件 **`signoff.content_changed`**（kind `signoff`，consumers `['notifications']`，標題「同意書內容已更新，請重新閱讀並同意」，收件人＝被取代那一版參與者快照裡的全部學生＋主指導），由 hook 在建新版時發；`signoff.superseded` 仍照舊發給系辦（系辦自己改的就 recipients 空）。這就是 #161 的答案（§6.4 有畫面）。只改對象、截止、標題不觸發新版。
- `response_rosters` 對同意書作業照常建立（**整組收件**，一列一組），用來算「繳交狀況」的分母與催繳名單；該組「已交」＝package 目前版本 `complete`，「未繳」＝`collecting`／`teacher_pending`／`revision`，「尚未建立」＝沒有包（§6.3）。
- `signoff_packages.item_id is null` 的舊資料：系辦在作業分頁底部看到一塊「舊同意書（未連結作業）」唯讀列，連到原詳情頁（路由轉址歸②）。測試站只有示範資料，凍結期用 `seed-demo --remove` 後重 seed（§1.7），正式站還沒開，所以不寫 SQL 回填。

### 1.3 評分項目 ↔ 作業連結（schema `grading.ts`）

- **新表** `grading_stage_settings (cohort_id uuid not null references cohorts(id), stage_key text not null, item_id uuid null references managed_items(id), description text null check (description is null or char_length(description) between 1 and 500), updated_by_user_id uuid not null references users(id), updated_at timestamptz not null default now(), primary key (cohort_id, stage_key), check (item_id is not null or description is not null))`。matrix 新列 slice `C20`：select／insert／update(`item_id`,`description`,`updated_by_user_id`,`updated_at`)／delete true（兩欄都清空＝刪列）。
- 為什麼不放進 `stages` jsonb：`stages` 寫了不可變、第一位老師填分後整版鎖定；對應作業與說明都**不影響分數**（連結只決定老師批改時看哪份繳交，說明只是給老師看的文字），系辦在學期中隨時要能改（例如期中之後才建「系統驗收文件」作業再掛上去、或補一句評分說明），放 jsonb 會逼著建新版＋套用重算。側表＝改了不建版、不鎖、不重算。**`description` 也放側表**，不進 jsonb，`normalizeSchemeStages` 不改。
- **stage_key 生命週期**：`SchemeEditor` 建新版時沿用既有 stage 的 `key`（`grading-forms.tsx:53,65`），只有新加的才補 `s{n}`（`scheme.ts:235`），所以 key 跨版本穩定。讀取規則：所有讀側表的查詢（`teacherBenchPage`、`GradingRulesPanel`、`PublicGradingQuery`）都 **join 目前已發布版本的 stages**，key 不在裡面的列不讀；`publish` 新版同交易內 `delete from grading_stage_settings where cohort_id=$1 and stage_key not in (新版 keys)`。沒有已發布版本時側表不可寫（`VALIDATION_FAILED`「請先發布評分規則」）。
- 沒有對應作業的評分項目（例如「態度」）＝`item_id null`＋`description`；老師只看到標題＋說明＋直接填分（細項只有一個「總分」是方案結構，在評分規則勾「直接填總分」時 UI 代填 `items=[{name:'總分',type:'number',max:100,weight:100}]`）。
- 驗證（application）：`item_id` 必須同屆、`collectsResponses`、`receiver_unit='group'`、非草稿、`consent_mode is null`；否則 `VALIDATION_FAILED`。

5. **催繳寄信量**：一次最多全屆（~60 人）；Brevo 10 s timeout、fire-and-forget；不做批次佇列（正式站規模小）。
6. **示範資料重 seed**：測試站凍結期執行；`--remove` 會拒絕有真實資料引用的情況（既有保護）。
